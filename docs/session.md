# Session Storage and Entry Model

This document is the source of truth for how coding-agent sessions are represented, persisted, migrated, and reconstructed at runtime.

## Scope

Covers:

- Session JSONL format and versioning
- Entry taxonomy and tree semantics (`id`/`parentId` + leaf pointer)
- Migration/compatibility behavior when loading old or malformed files
- Context reconstruction (`buildSessionContext`)
- Persistence guarantees, failure behavior, truncation/blob externalization
- Storage abstractions (`FileSessionStorage`, `MemorySessionStorage`, the `SqlSessionStorage` schema) and related utilities

Does not cover `/tree` UI rendering behavior beyond semantics that affect session data.

## On-Disk Layout

Default file-session location:

```text
~/.omp/agent/sessions/<encoded-cwd>/<timestamp>_<sessionId>.jsonl
```

`<encoded-cwd>` is derived from the canonicalized cwd (so symlink aliases share a bucket): `-<relative>` for directories under home, `-tmp-<relative>` for directories under the temp root, and `--<encoded-absolute>--` for anything else, with path separators replaced by `-`.

On access, buckets written by the short-lived hashed scheme (`<scope>-<project-basename>-<sha256(canonical-cwd)>`, used in 17.2.5-17.2.8 and reverted in 17.2.9 by #7397) are migrated back into the path-encoded names best-effort, along with older `--<home-encoded>-*--` spellings of home-relative buckets.

Blob store location:

```text
~/.omp/agent/blobs/<sha256>
```

Terminal breadcrumb files are written under:

```text
~/.omp/agent/terminal-sessions/<terminal-id>
```

Breadcrumb content begins with cwd and session file path. Optional extra lines are `fresh` and `cwdstat <device> <inode>`. A fresh breadcrumb preserves an initially created, lazy session whose JSONL file does not exist yet, preventing `continueRecent()` from reopening the previous session. Explicit `newSession()` boundaries materialize their header before returning, except the lazy successor created by `drop` (`/delete`). The directory identity permits automatic re-rooting after a same-filesystem project rename; a missing cwd alone is not move evidence. Writes are synchronous, ordered, and best-effort.

## File Format

Session files are JSONL: one JSON object per line. Current files physically begin with a fixed-width, 256-byte `type: "title"` slot (including its newline), followed by the session header and then `SessionEntry` values. Legacy files may begin directly with the header. Loaders strip the physical slot and fold its current title/source into the logical header.

- The logical first entry is always the session header (`type: "session"`).
- Remaining logical entries are `SessionEntry` values.
- Ordinary appends extend the tree; branch navigation moves an in-memory pointer (`leafId`). Targeted rewrite helpers can change existing records.

### Header (`SessionHeader`)

```json
{
	"type": "session",
	"version": 3,
	"id": "019c625b-b900-7000-8000-000000000001",
	"timestamp": "2026-02-16T10:20:30.000Z",
	"cwd": "/work/pi",
	"title": "optional session title",
	"titleSource": "auto",
	"additionalDirectories": ["/work/shared"],
	"previousSessionFiles": ["/old/location/session.jsonl"],
	"providerPromptCacheKey": "optional inherited cache identity",
	"taskPromptCacheKey": "optional local-only Task sibling family key",
	"parentSession": "optional lineage marker"
}
```

Notes:

- New session ids are UUIDv7 strings; readers also accept older string ids.
- `additionalDirectories` records normalized, deduplicated workspace roots beyond `cwd`.
- `previousSessionFiles` records prior absolute locations after successful moves.
- `providerPromptCacheKey` carries an inherited provider prompt-cache identity for eligible full forks.
- `taskPromptCacheKey` is a local-only Task sibling family key (`<parent cache key>:<agent name>`), omitted from shares and HTML exports.
   - The executor derives it once the child session exists, regardless of the child's initial model. An empty parent cache lineage derives nothing, so those children keep their own session identity.
   - Until a request uses it, the key lives in a session-scoped, non-persisted stash. The first primary request on a model that opts into `shared-prompt-cache` writes it to the header, so fork and reopen keep it.
   - Each request decides consumption against its own model: an explicit session key wins; otherwise the family key applies only on opted-in models.
   - The stash does not survive a fork, move, branch, new-session reset, or switch to a different session; a rolled-back move or switch restores it.
- `parentSession` is an opaque lineage string. Current code writes either a session id or a session path depending on flow (`fork`, `forkFrom`, `createBranchedSession`, or explicit `newSession({ parentSession })`). Treat it as metadata, not a typed foreign key.

- `titleSource` is `auto` or `user`; automatic renames cannot overwrite a user title.

### Entry Base (`SessionEntryBase`)

All non-header entries include:

```json
{
	"type": "...",
	"id": "8-char-id",
	"parentId": "previous-or-branch-parent",
	"timestamp": "2026-02-16T10:20:30.000Z"
}
```

`parentId` can be `null` for a root entry (first append, or after `resetLeaf()`). Generated entry ids are normally eight hexadecimal characters, with a full Snowflake id as the collision-exhaustion fallback; consumers must not assume a fixed width.

## Entry Taxonomy

`SessionEntry` is the union of:

- `message`
- `model_usage`
- `thinking_level_change`
- `model_change`
- `service_tier_change`
- `compaction`
- `branch_summary`
- `reset_boundary`
- `custom`
- `custom_message`
- `label`
- `title_change`
- `ttsr_injection`
- `credential_pin`
- `session_init`
- `mode_change`

### `message`

Stores an `AgentMessage` directly.

```json
{
	"type": "message",
	"id": "a1b2c3d4",
	"parentId": null,
	"timestamp": "2026-02-16T10:21:00.000Z",
	"message": {
		"role": "assistant",
		"api": "anthropic-messages",
		"provider": "anthropic",
		"model": "claude-sonnet-4-5",
		"content": [{ "type": "text", "text": "Done." }],
		"usage": {
			"input": 100,
			"output": 20,
			"cacheRead": 0,
			"cacheWrite": 0,
			"totalTokens": 120,
			"cost": {
				"input": 0,
				"output": 0,
				"cacheRead": 0,
				"cacheWrite": 0,
				"total": 0
			}
		},
		"stopReason": "stop",
		"timestamp": 1760000000000
	}
}
```

The persisted `message.role` discriminant is **camelCase**, not the snake_case used by
the LLM wire format or extension hook names. Ordinary conversation records use these
roles under `type: "message"`:

| Persisted `message.role` | Owner package | Notes                                                                             |
| ------------------------ | ------------- | --------------------------------------------------------------------------------- |
| `user`                   | pi-ai         | User/tool-feedback turn.                                                          |
| `developer`              | pi-ai         | Developer-role instruction turn.                                                  |
| `assistant`              | pi-ai         | Model turn; tool calls live in its `content` as `{ "type": "toolCall" }` blocks.  |
| `toolResult`             | pi-ai         | Result of one tool call — **not** `tool_result`. Carries `toolCallId`/`toolName`. |
| `bashExecution`          | pi-tui        | Standalone `!`-bash run.                                                          |
| `pythonExecution`        | pi-tui        | Standalone Python run.                                                            |
| `hookMessage`            | pi-tui        | Legacy hook-injected message, retained for migration; new code uses `custom`.     |
| `fileMention`            | pi-tui        | Inlined `@file` mention contents.                                                 |

Branch and compaction summary roles are synthesized from dedicated top-level entries
during session-context reconstruction. Extension messages sent through `pi.sendMessage`
likewise persist as `custom_message` entries and reconstruct as `custom`:

| Persisted entry type | Reconstructed role  |
| -------------------- | ------------------- |
| `branch_summary`     | `branchSummary`     |
| `compaction`         | `compactionSummary` |
| `custom_message`     | `custom`            |

Internal callers can append a `custom` message directly, so readers must discriminate on
`entry.type` rather than infer the persisted shape from the reconstructed role.

`toolCall` is a **content-block type inside an `assistant` message's `content` array**, not
a message role. An extension keying off `message.role` that matches snake_case constants
(`tool_result`, `tool_call`) or lowercases the role before comparing will silently skip
`toolResult` (and every other camelCase role) — no error is raised. Match the camelCase
values above verbatim. The base roles are `Message` in `packages/ai/src/types.ts`; the rest
are merged into `CustomAgentMessages` (`packages/agent/src/compaction/messages.ts`,
`packages/tui/src/chat/messages.ts`). Coding-agent re-exports the custom types and
converts them for provider context in `packages/coding-agent/src/session/messages.ts`.

An `assistant` message the session's own loop produced also carries `promptCacheModelKey`: the model its request went
out as, as the prompt cache keys it (a JSON array string of provider, model id, wire API and the endpoint as `fetch`
reaches it: scheme and host in lower case, no default port, no trailing slash, and no userinfo, query or fragment, the
parts a provider's key can sit in, which this record would otherwise write to the session file). The session stamps it
at `message_end`, before the entry is written. It is a stored-format addition, like the optional `settingsRead` of a
`system-prompt` record, because no other record names the endpoint a request went to: a resumed process compares it
with the key its own requests go out under, so after a `models.yml` base URL change to another server or path between
processes the cache status and the transcript-prompt restore treat the entry the other server holds as a model change;
a change of only the base URL's userinfo, query or fragment is not one. A message without it (written by an
earlier release) compares by provider, model id and `api`, as before. Providers build their wire messages from named
fields and never send it (the pi-native transport hands its gateway whole messages, `completedAt` among them). `/resume`,
`/fork`, `omp --fork` and `/tree` branch copies keep it with the rest of the message.

### `model_usage`

Records model calls outside the conversation transcript. Fields are `purpose`,
optional model `role`, `api`, `provider`, `model`, `usage`, `stopReason`, and
optional `errorMessage`. These records contribute usage accounting, not model
messages or transcript turns. `appendModelUsage()` attaches the record to the
initiating session/branch and rejects stale session ownership.

### `model_change`

```json
{
	"type": "model_change",
	"id": "b1c2d3e4",
	"parentId": "a1b2c3d4",
	"timestamp": "2026-02-16T10:21:30.000Z",
	"model": "openai/gpt-4o",
	"role": "default"
}
```

`role` is optional; missing is treated as `default` in context reconstruction.
`resolvedModelIsFallback` optionally marks a transition onto a model other than
the requested one: a retry fallback, or a model that replaced the requested one
when the session started. The reserved role `fallback` is ephemeral: model
restoration prefers the configured default instead of restoring that role's
temporary model.

### `service_tier_change`

```json
{
	"type": "service_tier_change",
	"id": "c1d2e3f4",
	"parentId": "b1c2d3e4",
	"timestamp": "2026-02-16T10:21:45.000Z",
	"serviceTier": { "openai": "priority", "google": "flex" }
}
```

`serviceTier` is a per-family map keyed by `openai`/`anthropic`/`google` (each value `auto`/`default`/`flex`/`scale`/`priority`/`ultrafast`), or `null` when no tier is active. Legacy entries that stored a single string (`"flex"`, `"openai-only"`, `"claude-only"`, …) are coerced to this map during context reconstruction; loading alone does not rewrite their payload.

### `thinking_level_change`

```json
{
	"type": "thinking_level_change",
	"id": "c1d2e3f4",
	"parentId": "b1c2d3e4",
	"timestamp": "2026-02-16T10:22:00.000Z",
	"thinkingLevel": "high"
}
```

`configured` may additionally preserve the selector the user chose (`"auto"` or a concrete level). Readers of older entries fall back to `thinkingLevel`. Both fields can be `null`; a null/missing resolved level reconstructs as `"off"`.

### `compaction`

```json
{
	"type": "compaction",
	"id": "d1e2f3a4",
	"parentId": "c1d2e3f4",
	"timestamp": "2026-02-16T10:23:00.000Z",
	"summary": "Conversation summary",
	"shortSummary": "Short recap",
	"firstKeptEntryId": "a1b2c3d4",
	"tokensBefore": 42000,
	"details": { "readFiles": ["src/a.ts"] },
	"preserveData": { "hookState": true },
	"fromExtension": false
}
```

Optional compaction metadata includes `tokensAfter`, `method`,
`providerReplayThroughEntryId`, and `warning`. `preserveData` can carry native
OpenAI/Anthropic replay state or a snapcompact archive; it is not just extension
state. `providerReplayThroughEntryId` marks the last entry represented by native
replacement history so later entries still replay normally.

### `branch_summary`

```json
{
	"type": "branch_summary",
	"id": "e1f2a3b4",
	"parentId": "a1b2c3d4",
	"timestamp": "2026-02-16T10:24:00.000Z",
	"fromId": "a1b2c3d4",
	"summary": "Summary of abandoned path",
	"details": { "note": "optional" },
	"fromExtension": true
}
```

If branching from root (`branchFromId === null`), `fromId` is the literal string `"root"`.

### `reset_boundary`

A payload-free marker appended by `/clear`. The collapsed live transcript and rebuilt model context begin after the latest applicable boundary; full-history transcript export still retains entries before it.

```json
{

	"id": "f1a2b3c4",
	"parentId": "e1f2a3b4",
	"timestamp": "2026-02-16T10:25:00.000Z",
	"customType": "com.example.my-extension.state",
	"data": { "state": 1 }
}
```

On resume, a valid latest `session_exit` after a non-terminal conversation tail causes `AgentSession`/SDK initialization to append a synthetic assistant message with `stopReason: "aborted"` and rebuild the display/agent context. A normal exit only triggers that transition when it recorded pending tool calls; abnormal exit kinds can trigger it without that list. This prevents the restored transcript from presenting an interrupted turn as still live.

A tool result named by a `tool_result_prune` record keeps its original content in the file until a later full rewrite writes the blanked content inline (the record stays; replaying it again changes nothing). Readers that tail the file by byte offset — the Agent Hub transcript viewer, the collab agent drawer, and RPC subagent streaming — cannot apply a record to a line they already emitted and show the original content.

An entry named by an `entry_patch` record keeps its original fields in the file until a later full rewrite writes the patched fields inline. A full rewrite writes every `entry_patch` record with an empty `patches` list, so a field that a later rewrite-only change replaced (images a later `/shake images` dropped from an elided tool result) is not restored when the file loads. `SessionManager.patchEntries` appends a record except when a target's line holds 4 MiB (`TRANSCRIPT_READ_CAP`) or more, newline aside: a collab guest fetches a transcript in replies of at most that size, each ending on a line break, so it cannot read such a line, and `patchEntries` rewrites the file instead, writing that line with the fields set. The size is the line's as the manager last loaded or wrote it, not that of the entry the caller already changed in place. `SessionManager.patchEntries` rejects, before changing anything, patches whose record as written the readers would skip, such as a `NaN` count, which the line holds as `null`. When entries share an id, a record sets fields on the last of them in the file: whole-file loads (`applyEntryPatches`), `EntryPatchReplay`, the stats parser (`packages/stats`) and the Python readers (`scripts/entry_patches.py`) all decide so. A session that keeps entries another writer appended to its file applies the records among them to the entries it holds, so its next full rewrite keeps those fields. The RPC server's subagent transcript (`get_subagent_messages`) applies the records in the bytes it reads to the entries it returns, and lists the records among its raw `entries`; a record that names an entry an earlier response returned changes nothing in its response. The RPC clients (the TypeScript `RpcClient` and the Python, Go and Rust SDKs) apply each response's records to its entries, list no record, and return each patch whose target the response lacks in `entryPatches` (`entry_patches` in Python and Rust, `EntryPatches` in Go); they keep, per session file, only the id and parent of each record they hid since the last response from byte zero or with `reset`, so an entry whose parent is a record an earlier response hid takes that record's parent; a caller that holds the earlier entries applies those patches to them (see [RPC](./rpc.md#subagent-subscriptions)). The Agent Hub transcript viewer and the collab agent drawer hold the entries they read since they last read the transcript from its start, and every record they read, so a record in a later window or reply applies to an entry an earlier one showed, and that entry is shown again; an entry read again carries the records read before it, and an entry gives back the values it held before the records once a later entry with its id arrives (a line read again, told by its JSON, is not a later entry, so two distinct lines with byte-identical JSON count as one line read again). The stats database and `scripts/session-stats/sync.py` store rows derived from patched entries: a sync whose new bytes hold a record that sets the content of an entry an earlier sync stored, or an entry with an id a record of an earlier sync names (the stats cursor's `patchTargets`, `ss_sessions.patch_targets`), derives the session's rows again. Binaries older than the record do not apply it and show the fields as first written. A malformed record, or a patch naming a missing entry, a field that entry's kind lacks, or a `content` of the wrong shape for the entry's role (a string for an assistant or tool-result message), is skipped with a warning and the session loads. Readers in `@oh-my-pi/pi-utils/entry-patches` that hold no entry, or read raw bytes or text, use `patchFitsMessageRole`, and `entryPatchMarkerAt` and `entryPatchRecordsIn`, which parse only the lines that hold a record.

These readers return raw entries, with neither record kind applied and each record listed among them: `loadSessionFile()`, `loadEntriesFromFile()`, `loadEntriesFromFileStream()`, `parseSessionEntries()`, `visitSessionFile()`, `visitEntriesFromFile()`, `visitEntriesFromFileStream()` and `visitEntriesFromChunksSync()`. The session picker applies the records of its 4 KiB prefix and its 32 KiB tail window to the entries its prefix holds and to the last turn its status reads, and the records its line scan read (from the file's start to the line it stopped at), then the tail window's, to the first prompt that scan finds past the prefix. A record past the prefix that the tail window misses and the scan did not reach is not read, and the prompt text the picker falls back to when no scan finds one (cut from the prefix's partial line) takes no record. The picker's search holds the messages of the file's first 4 KiB as stored, so a record that shortens an entry brings no later text into it.

### `custom_message`

Extension-provided message that does participate in LLM context. `content` can be a string or text/image content blocks, and `attribution` records whether the user or agent initiated it. `timestamp` is the time of the message the agent took, which the rebuilt message carries, not the time the entry was written: the image clamp's `provider-image-drop` records and the date/cwd reminder's placements name a turn by its role and timestamp, so a session read again must find the turns its requests sent.

```json
{
	"type": "custom_message",
	"id": "a2b3c4d5",
	"parentId": "f1a2b3c4",
	"timestamp": "2026-02-16T10:26:00.000Z",
	"customType": "my-extension",
	"content": "Injected context",
	"display": true,
	"details": { "debug": false },
	"attribution": "agent"
}
```

```json
	"type": "label",
```

### `title_change`

Append-only audit entry for a session rename. It records `title`, `source` (`auto` or `user`), and optionally `previousTitle` and `trigger`. The current title is also updated in the fixed-width title slot so listing does not require a full-file rewrite.

## Versioning and Migration

### v1 -> v2

Applied when header `version` is missing or `< 2`:

- Reconstructs a linear parent chain using file order.
- Migrates compaction field `firstKeptEntryIndex` -> `firstKeptEntryId` when present.
- Sets header `version = 2`.

Applied when header `version < 3`:

- For `message` entries: rewrites legacy `message.role === "hookMessage"` to `"custom"`.
- Sets header `version = 3`.

### Migration Trigger and Persistence

- Migrations run during session load (`setSessionFile`).
- If any migration ran, the in-memory representation is marked for a full rewrite rather than rewritten immediately.
- The next persistence operation performs the full rewrite before incremental appends continue.

## Load and Compatibility Behavior

`loadEntriesFromFile(path)` behavior:

- Missing file (`ENOENT`) -> returns `[]`, unless `throwIfMissing: true` requests an error.
- Transcripts of at least 8 MiB stream through the JSONL loader from any storage with `readChunks` (file storage, and indexed storage whose backend reads in chunks, such as SQL and Redis); smaller ones, and storages without it (an SDK backend without `readChunks`), use a full text read.
- A streamed read that a full rewrite or delete cuts short (`SessionReadConflictError`, or `ENOENT` after bytes were read) starts again from the beginning, up to three times, and never returns the part read before. A path that the next read finds gone is a missing file, as above. The conflict is thrown after the last retry.
- Malformed records are skipped and counted by the lenient JSONL parser.
- The optional fixed-width title slot is removed and folded into the header.
- If the first logical entry is not a valid session header (`type !== "session"` or missing string `id`) -> returns `[]`.

`SessionManager.setSessionFile()` behavior:

- Missing or genuinely empty files initialize a new session at that exact path and materialize its header immediately. `SessionManager.open(..., { throwIfMissing: true })` instead rejects missing/empty input.
- Non-empty data without a valid leading session header is rejected without modifying the file. An array-only `loadEntriesFromFile()` result of `[]` therefore does not distinguish empty from corrupt input; the manager uses `loadSessionFile()` diagnostics.
- Valid files are loaded, migrated if needed, `tool_result_prune` records applied to the tool results they name, `entry_patch` records applied to the entries they name, blob refs resolved, then indexed. Migrations, skipped malformed records, and loaded OpenAI replay sanitization mark the next persistence operation for a full rewrite.
- Fail-closed opens (`throwIfMissing`) digest the content they parse, digest the current content again after cwd adoption, and reparse only when the two differ, so a stable transcript is parsed once. Size, modification time, and inode are not trusted: an in-place rewrite can keep all three, and an indexed backend's stat reads only its local index. Deletion (including a row removed from a Redis or SQL backend), truncation, and replacement still fail closed.
- A recorded cwd is adopted only when it is enterable. Otherwise runtime cwd stays at the launch/current directory while the transcript remains in its original location; workspace-root edits stay runtime-only until relocation.

## Tree and Leaf Semantics

The underlying model is append-only tree + mutable leaf pointer:

- Ordinary append methods create one new entry whose `parentId` is current `leafId`, then advance the leaf.
- `appendMessageToBranch()` appends to an explicit parent without moving the active leaf. `appendModelUsage()` likewise retains a successor branch's leaf when the initiating parent is no longer active.
- `branch(entryId)` moves only `leafId`; existing entries remain unchanged.
- `resetLeaf()` sets `leafId = null`; next append creates a new root entry (`parentId: null`).
- `branchWithSummary()` sets leaf to branch target and appends a `branch_summary` entry.

`getEntries()` returns all non-header entries in insertion order. There is no separate persisted leaf field: loading rebuilds the leaf from the last physical entry. Pointer-only `branch()`/`resetLeaf()` changes therefore need a subsequent append to survive reload. `discardEntryDurably()` only appends: a metadata branch marker under the discarded entry's parent, then, when the entry's children are all `service_tier_change` entries, fresh copies of them. The entry and its subtree stay in the journal off the active branch, so a discarded assistant turn's usage still counts in session totals, and the discard survives a restart while full rewrites fail.

`createBranchedSession(leafId, { copyArtifacts? })` creates a new identity containing only the selected root-to-leaf path. It drops old label records and recreates the resolved labels for retained entries after the last one, under new ids; an entry written after a dropped label (a title, an extension record, a warm refresh's usage) takes that label's parent as its own, so every retained entry points at one the copy holds and the copy's branch reaches the root. Unlike a full fork, it does not inherit the provider prompt-cache key. With `copyArtifacts` (used by `AgentSession.fork(entryId)`), the artifacts directory is copied in the background and the new artifact manager waits for the copy before allocating ids or resolving `artifact://`, as for a move to a sibling file.

## Context Reconstruction (`buildSessionContext`)

`buildSessionContext(entries, leafId?, byId?, options?)` resolves what is sent to the model. `options.transcript: true` instead builds a display transcript. Full transcript mode preserves compactions inline; `collapseCompactedHistory` renders only the current compacted tail, and `keepDanglingToolCalls` preserves still-running tool calls during a mid-turn UI rebuild.

Algorithm:

1. Determine leaf:
   - `leafId === null` -> return empty context.
   - explicit `leafId` -> use that entry if found.
   - otherwise fallback to last entry.
2. Walk `parentId` to root, stopping on a repeated id to bound corrupt cycles, then reverse to root->leaf.
3. Derive runtime state across the path:
   - resolved and configured thinking selectors from latest `thinking_level_change`
   - service tier from latest `service_tier_change`
   - model map from `model_change` entries (`role ?? "default"`); assistant-message inference is legacy fallback only until an explicit default is seen
   - deduplicated `injectedTtsrRules`
   - mode/modeData from latest `mode_change` (default mode `"none"`)
4. Choose the emission boundary:
   - a later `reset_boundary` hides everything through that boundary from model context and collapsed live transcript
   - otherwise the latest compaction emits its summary plus kept/post-compaction messages (provider-native replacement history may supply the kept model context)
   - full transcript export retains pre-reset history and renders compactions chronologically
5. Convert `message`, `custom_message`, and `branch_summary` entries into messages. Other entry types only affect replay state or metadata.
6. Remove dangling tool calls from replay (unless explicitly retained for a mid-turn transcript), neutralizing protected reasoning metadata on rewritten turns; drop unsafe aborted/error assistant turns and their paired tool results from model context.

## Persistence Guarantees and Failure Model

### Persist vs in-memory

- `SessionManager.create/open/continueRecent/forkFrom` -> persistent mode (`persist = true`).
- `SessionManager.inMemory` -> non-persistent mode (`persist = false`) with `MemorySessionStorage`.

### Write pipeline

Ordinary completed appends update memory and local file storage synchronously once the lazy file-creation gate has been crossed. There is no `fsync`, so successful local writes protect against software crashes, not power loss. Indexed Redis/SQL backends update their local view immediately but publish remotely in an ordered async queue; `flush()`/backend drain is required to confirm those writes. While the lines an indexed store has queued and not yet settled hold more than 64 MiB, an agent turn on that store waits before each model request and before each tool result is appended, until enough of them settle or the turn is aborted (`waitForAppendAdmission`); another store's backlog never holds it. Under the threshold the method returns `undefined`, so a turn has nothing to await. Appends made meanwhile still queue, and a writer's `append` resolves once its own line is stored, so 64 MiB is where turns start to wait, not a bound on the queue. A wait that lasts 10 s logs one warning (`Session append admission still waiting`) with the bytes queued. Title changes and atomic batches have their own awaited persistence paths. Streaming partial text is not persisted until the completed message is appended.

- A new ordinary session remains memory-only until it contains an assistant message or a caller invokes `ensureOnDisk()`.
- Before that gate, entries remain in memory; crossing it writes the full title slot, header, and accumulated entries.
- Explicit `newSession()` (including `/new`) calls `ensureOnDisk()` before returning, preserving an empty session boundary across terminals. The `/delete` successor (`drop`) is the exception: it stays lazy, because the fresh terminal breadcrumb already pins this terminal to it and a failed deletion leaves the predecessor as a legitimate resume target; a zero-turn quit must not leave an empty file.
- Afterwards, entries append incrementally.
- Saving an editor draft forces a discoverable header and stores `draft.txt` with a marker; if the draft disappears while only startup metadata remains, close removes that draft-only session. Explicit `ensureOnDisk()` sessions remain resumable.
- Concurrent completed appends supersede an in-flight atomic rewrite with an authoritative full-body rewrite so stale publication cannot clobber them.
- A queued indexed full rewrite stays non-current until confirmation. When a fenced rewrite lands after a successor supersedes it, the manager validates that durable body and records its byte size before retrying the newer transcript.
- With `secrets.maskSessionStore` on, every write above masks a copy of what it writes: each entry, the header, the title slot, the title the store keeps and the draft. Under file storage, the title and the recaps recorded in `history.db` are masked too. Secret values the agent holds become markers such as `[REDACTED:env:NAME]`, and the live entries keep the values. An `entry_patch` record stays one appended line, and each of its patches is masked as the same fields are in the stored line of the entry it patches: a signed block whose text masking changes loses its signature, and a field that entry keeps stays as written, so the entry a load patches is the one a full write stores. The manager reads the setting per session, at each write: the code that gives it to a session binds it to that session's settings (`setStoreMasking`), so the sessions of one process can differ. A manager that no session binds reads the settings that the process itself runs with, from every layer, the project config included. See [Secrets in stored sessions](./secrets.md#secrets-in-stored-sessions).

### Durability operations

- `flush()` drains async disk/storage queues and the open writer (no `fsync`); `flushSync()` drains synchronously supported work or rewrites a non-current file. It cannot confirm queued remote publication; those backends still require awaited `flush()`/drain.
- Atomic full rewrites use storage `writeTextAtomic` with a commit guard and expected byte-size precondition; file storage stages then renames over the target, including an EPERM-safe move-aside fallback. A rewrite whose acknowledgement fails still counts as published when the stored bytes match the intended body, except inside `appendEntriesAtomically()`. File storage compares the file's bytes exactly as they stream; other storage compares the byte length and SHA-256 of the chunks it yields (its whole text as one chunk when it has no `readChunks`).
- File-backed full rewrites lazily generate JSONL records and periodically hint garbage collection, so they do not retain a second transcript-sized line array.
- `SessionManager` hands full rewrites over as lines (`writeLinesSync`/`writeLinesAtomic`) to a storage that takes them, so file storage, and indexed storage whose backend has `writeFullStream`, never hold the body as one string; a storage without them (`MemorySessionStorage`) gets the joined text. File storage streams the lines into its staging file. Indexed storage whose backend has `writeFullStream` (Redis and SQL) spools them, in writes of about 1 Mi UTF-16 units, into a file under `<os temp>/omp-spool-<uid>/`, a directory private to the account (mode 0700; the store uses it only when `lstat` finds a directory this account owns with mode 0700, so not a symlink, nor a directory another account made first), that is unlinked as soon as it is open (so a killed process leaves nothing), then publishes from the spool through `writeFullStream`: SQL's staged swap below, or Redis's, which appends each part of at most 1 MiB, cut between characters, to a staging key of the write's own (`<prefix>staging:<path>#<random UUID>`, which expires an hour after its last part, and which no listing scans), then runs one script that checks the session's size and the staged length, renames the staging key over the file key, clears its expiry and sets the mtime, title and write generation, or deletes the staging key and changes nothing when a check refuses; a failed write deletes its staging key too. `writeLinesAtomic` opens and writes its spool asynchronously, so the event loop keeps running while a large body is prepared, and prepares it while the path's earlier writes settle; an array of lines it is handed is read from a copy of that array taken when it is called, so the caller may change its array meanwhile (the session manager's lazily serialized body is read as the body is prepared, never held whole). `writeLinesSync` spools synchronously. A backend without `writeFullStream` (an SDK backend) gets the joined lines through `writeFull`, with no spool. A failed atomic publish still counts as landed when the stored bytes match the spool by size and SHA-256. Where the platform has no account id (Windows) no spool is made, since there is no owner to check the spool directory against and a file there takes its directory's access list: the store reads the lines once when the rewrite is queued, into blocks of at most 1 MiB of their bytes, each kept zstd-compressed (level 3) in memory (`writeLinesAtomic` compresses them off the event loop), and publishes from those blocks exactly as from the spool, with no warning. Such a rewrite keeps a compressed copy of its body in memory while it is queued, and publishes the bytes its lines held when it was queued, whatever changes in the entries after. When the spool cannot be used (its directory or file cannot be made or opened, as under a read-only `os.tmpdir()`, a write to it fails, as on a full disk, or its directory is refused), the store logs one warning, not one per rewrite (a spool file already opened is closed and removed), and streams the rewrite to `writeFullStream` straight from the lines, never joined: it reads the lines once when the rewrite is queued, for the body's size, SHA-256, title slot and session id (`writeLinesAtomic` lets the event loop run between the chunks of that read), and again, in chunks of at most 1 MiB, as the write takes them; the stream fails at its end, so the backend swaps nothing in, when that second read gives other bytes. Lines that can be read only once are read into an array first. When that write fails, the rewrite fails as any failed publish does, the stored copy stays as it was, and the store logs an error naming the session id, the path and the cause (a size conflict or a lost claim, which the caller resolves, is not logged); the next full rewrite tries the spool, then this, again. On file storage a subclass or spy that overrides `writeTextSync`/`writeTextAtomic` keeps receiving the joined body; indexed storage streams lines past such an override, so one that must see every rewrite overrides `writeLinesSync`/`writeLinesAtomic` too.
- Indexed storage has `readChunks` only when its backend has one (SQL pages through the parts; Redis reads windows of at most 1 MiB, one script each, see below), so a reader that finds it reads in bounded pieces; it reads the bytes `readText` reads, with the indexed title laid over the first 256 bytes (a body shorter than the title slot reads as the slot alone). Over a backend without it (an SDK backend) each of these readers reads the transcript whole, once. Loading, `scanLines`, copying a session's subagent transcripts (`copyTranscriptTree`, which appends what it reads through a writer in batches of whole lines of about 1 Mi UTF-16 units, so a line longer than that goes whole in one batch), the working copy `omp render` makes of a session outside file storage, the debug report, blob gc's reference scan and memories stage 1 read through it. The check of the stored copy after a failed atomic publish reads the backend's own chunks, so over a backend without them it reads the stored copy whole. RPC `get_subagent_messages` and the Agent Hub transcript viewer read through `readTextFrom` in windows of at most 8 MiB (larger only for a line longer than 4 MiB) and read on from where the window's complete lines end; SQL and Redis fetch only about the window's bytes, while a backend without `readFrom` is read whole and the window cut out.
- Redis's `readChunks` runs one script per window, which returns the key's size, the session's write generation and at most 1 MiB of its bytes. Each window starts and ends between UTF-8 characters, so its bytes decode and encode back unchanged: a read from inside a character fetches that character whole and yields its bytes from the requested offset, and a window that stops short of the read's end ends before the character its next byte continues. The read stops at the size its first window saw, so an append made meanwhile is left out. A key that is gone, or shorter than that size, at a later window fails the read with `SessionReadConflictError` before that window yields anything; a missing key at the first window is `ENOENT`. The generation is kept in the `<prefix>generation` hash as `<token> <mtime>`: a full write, a move or a delete gives the session a new token whatever bytes it leaves; an append or a title update keeps the token while the mtime recorded beside it is the one the meta hash holds, and takes a new one when it is not. A window reads the token while those two mtimes agree, and no token when they do not, which is when an earlier version, which sets the mtime and keeps no generation, wrote the session last. A read whose first window found the token fails at a later window at another generation: a rewrite by this version to as many bytes or more is a read conflict too, and so is any write of an earlier version, an append included, except one that sets the very mtime recorded, or one made in two commands, the bytes and then the mtime, with the window between them. Full writes and appends have been one script since v17.1.0 (commit 4bc68b45e25), so only a release before that writes them in two commands. A move is two commands (a rename, then the mtime) in every upstream release through v19.1.1; this fork makes it one script since commit 3b60887237b. Builds v18.18.6-sami.20261119-162325 and v18.18.6-sami.20261123-024918 carry both scripts, so neither case arises where only such builds write. A read whose first window found no token runs as before generations: a later window that finds a token (this version wrote since) fails it, an earlier version's append does not, and once it has yielded more than one window, one more script, when the read ends or its consumer closes it early, checks that the key still holds each window's bytes by length and SHA-1, the windows having returned their SHA-1; such a read does not see an earlier version's rewrite to more bytes that keeps the windows it read. While builds with and without generations write one store, a read therefore conflicts at most once more for the change between the two kinds of read. Readers then read the transcript again from its start, as they do on SQL.
- Local appends and publication share a cross-process publish lock. A changed byte size raises `SessionWriteConflictError`; lock contention raises `SessionLockError` without publishing the staged rewrite. This is not a content-hash comparison and cannot protect against non-cooperating external writers.
- `FileSessionStorage` holds a process-owned OS lease on each session a process writes, keyed by the session id rather than the file's path, so every process that reaches one journal (through a symlink, a hard link, or after a move) meets the same lease. The lease is `pi-utils` `tryAcquireFileLock` on `<session-owners>/<session-id>`, where `<session-owners>` is `~/.omp/run/session-owners` (XDG: `$XDG_STATE_HOME/omp/run/session-owners`), shared across profiles: on Windows a named mutex, which creates no file; on Linux an open-file-description (`F_OFD_SETLK`) lock and on macOS and other Unix a `flock`, both on a sidecar in that directory. On Linux a lease whose abstract-socket name an older omp build still binds also counts as held. Only write paths claim it, so the first process to write a session owns it; opening a session to inspect it (`omp share`, `--export`, `render`) never does. Managers in one process share the lease; it is released on close or a session switch, and the kernel drops it when its process exits. Processes with different home or state directories do not meet in this lease. A plain copy of a session file keeps its id, so a process writing the copy while the original's writer is live moves to a sibling; a collab guest's replica takes its own id (`parentSession` is the host's) so it never contends with the host.
- A process never writes a session whose lease another live process holds: its first write moves the session to a fresh sibling `<timestamp>_<new-session-id>.jsonl` in the same directory, publishes the whole in-memory transcript there once, and continues appending incrementally. The owner's file is left untouched. Like `fork`, the sibling gets a new session id with `parentSession` pointing at the old one and keeps the provider prompt-cache key, so resume-by-id, the title index, and the picker never see two files for one id. The artifacts directory is copied in the background without overwriting files the moved session has already written; its artifact manager waits for the copy before allocating ids or resolving `artifact://`, and `flush()`/`close()` await it. `local://` and `agent://` reads that bypass the artifact manager can miss pre-move files until the copy finishes.
- Under `OMP_SESSION_EXCLUSIVE=1` an explicit resume (`--resume`, the session `--continue` picks, the picker's pick) does not wait for its first write: it takes the lease before `session_start`. While another live process holds it, the resume says so on stderr and tries again every 100 ms for up to 35 s, the time a launcher's previous process on the session may still take to end; then it holds the session under its own id. One still held after that ends the process non-zero (`open-elsewhere`) before anything writes it. Without the variable a resume claims at its first write, as above: the kernel drops a dead holder's lease at once, so there is nothing to wait for.
- `moveTo()` refuses, before anything moves or any directory is created, to move a session another live process writes or to replace a destination file whose session (by its header id) another live process writes.
- Another program can check ownership without claiming: `isSessionLeaseHeld(sessionId)`, `omp session lease --json -- <id>...` (`{"held": [...], "unknown": [...]}`), and RPC `get_session_lease` observe the lease without taking it (an `F_OFD_GETLK` query plus a connect probe of the older abstract-socket name on Linux, `F_GETLK` on other Unix, a `\BaseNamedObjects` directory listing on Windows), so they never make a concurrent claim fork the session.
- Under `bun test`, the lease directory is `<os temp>/omp-test-session-owners-<uid>` instead of the real state directory. It is exported as `PI_TEST_SESSION_OWNERS_DIR` when `session-storage` loads, and an omp process a test spawns derives the same directory from the `PI_TEST_RUNTIME=1` marker that every child of a test inherits (`scripts/test-preload.ts`). A test that builds a child's environment from nothing, or removes that marker, must pass `PI_TEST_SESSION_OWNERS_DIR` itself.
- On the file and memory backends, a `SessionWriteConflictError` on durable bytes during a full rewrite means a writer without the lease (an older omp, an external tool) changed the file. The manager reads it back, keeps the entries it lacks as a side branch (the active leaf stays its own), and retries against the size it read, up to three times per rewrite. If that writer changes the file inside every retry, the session leaves the file to it and moves to a sibling (`reason: "contested"`) rather than re-serializing the transcript on every later write. A deleted file is recreated; a file that no longer reads as this session is left untouched and the session moves to a sibling. Indexed backends keep reporting the conflict, since there it can be the manager racing its own unconfirmed publish.
- `appendEntriesAtomically()` groups a synchronous callback's appends into one atomic publication. Failure rolls back staged entries and repairs retained concurrent work, including a publish whose acknowledgement failed after its body landed.
- Rewrites serve renames, entry rewrites, migrations/sanitization, move/fork, and recovery. A session-title change appends its `title_change` entry like any other entry and updates the fixed-width title slot in place instead of rewriting the body; field updates `patchEntries()` describes (retry markers, compaction stamps, elide passes) append an `entry_patch` record instead. `patchEntries()` resolves once pending writes settle; like an append, a failed write is latched and reported, not thrown, and the fields stay set for the next write to land.

### Error behavior

- The manager records what the session file is proven to hold: the entries a load or a successful write left there, and the file's byte size. An append writes every entry past that record in order, in chunks of whole entries of at most 4 MiB each (an entry larger than that goes alone), and the record advances as each chunk lands, so after a failed append, or a failed full rewrite that carried entries the file lacked, the next append restores the missing entries before their successors, resuming after the last chunk that landed. A file that grew past the record by whole entries, this manager's own next ones followed only by entries another writer added under known parents or as roots (a resumed session's previous process writing its exit marker, or the original of a cloned manager restoring an entry both hold), is read back only past the record; those entries are kept, the record extends over them, and appending continues. A root is kept only while the file's header, read from a bounded prefix, still names this session: another session's journal that replaced a header-only file measures the same and starts with a root, and that file republishes instead, which moves the session to a sibling. A structural change (migration, a session switch, entries adopted from another writer during a conflicting rewrite) or any other file whose size does not match the record republishes the whole journal instead; a rolled-back atomic batch keeps the record when none of its entries reached the file. Content-only changes (`rewriteEntries()` after in-place edits, header changes, the title slot) never gate appends: if their full rewrite fails, turns keep saving and the next successful full rewrite carries the change, so until then a restart shows the earlier content. `rewriteEntries()` persists content changes; re-parenting entries in place is not supported. Failures are logged once with session-file context rather than thrown into the turn loop; `flush()`, `flushSync()` and `close()` surface a failure only while an entry is still missing from storage, and surface the latest one (`getPersistenceFailure()`), not an earlier failure that has since cleared.
- `flush()`, `close()` and `newSession()` restore missing entries only by appending them, and only while the file still measures what the record says, after keeping entries another writer appended as above. A file that vanished, grew in any other way, or needs a republish is left to the next append, so these calls never start a full rewrite.
- From the moment `dropSession()` starts deleting the current session file, nothing the manager starts writes that path: no append, heal, rewrite or title write. A publish already on the disk queue lands before the delete; an authoritative repair already in flight is abandoned and waited for before the delete. Entries recorded meanwhile stay in memory past the record, rewrites and titles wait, `flush()` and `close()` wait for the delete to settle, and `flushSync()` returns without writing or throwing.
- The file counts as gone when the delete succeeds, or when it fails and a stat of the journal then fails with `ENOENT`: the file backend unlinks the journal before it removes the artifact directory, and an indexed backend's remove can fail after it deleted the session row, so a delete can fail with the journal already gone. Any other stat result counts as present. Once gone, the file's persistence ends even if the delete failed: the entries stay in memory, those recorded during the delete are discarded with the file, nothing writes that path again, the next `newSession()` or `setSessionFile()` starts from there, and a failed delete still rethrows.
- When the delete fails with the journal present, the session keeps saving as before, by append alone where a full rewrite cannot land (a read-only directory). A title set during the delete is written to the title slot in place; a full rewrite runs only for an in-place edit or abandoned publish that waited, or when the slot write fails. The next append, `flush()` or `close()` appends the entries recorded during the delete and any that missed the journal before it, or reports the failure. On an indexed backend the whole journal is instead published once, checked against the stored size: a remove can fail after deleting the session row while the readback of that row fails too, and then the publish reports the missing row rather than an append recreating it without its header. That publish runs before `dropSession()` returns when any entry is unsaved (a turn or title recorded during the delete, or a turn the backend rejected before it), since `flush()`, `close()` and a session switch only append; otherwise it is the next write. The next `newSession()` for the same entries switches without appending the entries the file is missing, so it writes nothing to that file. The file, memory and indexed backends all behave this way.
- `AgentSession` folds a hidden persistence warning into the next prompt after `onPersistenceError`, so the agent can preserve critical work before continuing an at-risk session.
- `onPersistenceNotice` reports a session moving to a sibling file as a `SessionPersistenceNotice` (`reason`, `from`, `to`); it latches nothing and never reaches `onPersistenceError`. Every notice raised so far is replayed to each new subscriber, like a latched failure. Interactive mode shows it as a warning, print mode on stderr, RPC as a `warning` notice frame, each with home-relative paths.
- Atomic batch and recovery paths attempt authoritative repair. If publication may have happened and repair cannot be proven durable, `SessionPersistenceIndeterminateError` fails closed with the original and recovery errors.
- Writer close propagates the first meaningful error. Final disposal seals the manager, making late appends/rewrites no-ops, then releases retained entries so a disposed manager cannot overwrite a revived transcript.

## Data Size Controls and Blob Externalization

Before persisting entries:

- Strings over 500,000 characters are truncated with `"[Session persistence truncated large content]"`, except signed/encrypted provider blocks, signature fields, validated Anthropic native web/tool-search history blocks, Anthropic server-compaction replay carriers, and Cursor server records (`cursorHistory` payloads), which must remain byte-exact for replay.
- Transient `jsonlEvents` is removed.
- If an object has both string `content` and numeric `lineCount`, line count is recomputed after truncation.
- Image data URLs in `image_url` fields are always content-addressed in the blob store and replaced with `blob:sha256:<hash>`, regardless of length. Base64 payloads at least 1,024 characters are externalized in image `content` blocks, `images[]`, snapcompact `frames[]`, and image-generation results.
- Redundant OpenAI Responses `thinkingSignature` copies are omitted when the authoritative reasoning item already exists in `providerPayload`.
- Spilled MCP tool results omit duplicate `details.structuredContent` when the rendered structured output already lives in their truncation artifact.

These projections leave the live entries unchanged. On load, ordinary persisted image references are resolved back to inline payloads. Snapcompact frames stay lazy until context reconstruction selects them. Archives with frames truncated by older persistence code fall back to their retained text or undamaged frames.

An entry of any depth `JSON.parse` reads (400,000 levels) persists: a tool returns any JSON, and a line holds what it returned. The projections above and the store masking of `secrets.maskSessionStore` keep their own stack instead of recursing, and an entry nested past 10,000 levels is written by a writer that keeps one too, so a deep entry costs milliseconds where `JSON.stringify` takes seconds past about 25,000 levels and runs out of stack near 40,000. A value that holds a cycle, which JSON cannot write, fails the write with a `TypeError` as `JSON.stringify` does.

## Older Entry Bodies (the Cold Store)

A persisted `SessionManager` keeps whole only the entries the model context reads: those of the current branch from the **cut** on. The cut is the first entry the context keeps of the newest compaction on the current branch (`firstKeptEntryId`, or the entry after `providerReplayThroughEntryId` when `firstKeptEntryId` is empty) and, for the current model, of the newest compaction that model can replay, whichever comes first. With no compaction on the branch, nothing on it leaves memory. An entry off the current branch (another branch of the tree) leaves memory wherever it lies. The cut is computed again after a load, after a compaction (once the context is rebuilt from it), after the leaf moves to another entry, and at the first build for a new model: a context built for a model whose provider or API differs from the model the cut was computed for (the context `/model` builds for the model it switches to, before it records the change, reads no cold entry); entries that cross it are converted or made whole again. A build that only measures a context and does not become the agent's (`buildSessionContext({ measureOnly: true })`, as a fallback's fit check for a candidate model does) moves no cut: the session stays on its model, so its older entries stay cold. An entry made whole keeps the place of its record, and when it goes cold again with the same values it takes that record back instead of writing a new one, so moving the leaf back and forth does not grow the store.

**Where the store lives.** Each loaded manager writes one file under `os.tmpdir()/omp-cold-<uid>/` (`<pid>-<uuid>`), a directory of mode 0700 that each account has to itself. The store uses that directory only when it is a directory (not a link to one) that the account owns with mode 0700, so a directory another account made first makes the store keep its records in memory instead (see below). The file is unlinked as soon as it is open, so its disk is freed when the descriptor closes and a killed process leaves nothing behind. Where the platform has no account id (Windows) the store makes no file and keeps its records in memory (see below): there is no owner to check the store directory against, and a file there takes its directory's access list. A record is the entry exactly as the manager holds it, with image data replaced by blob references: it is not masked (see [secrets](./secrets.md#older-entry-bodies-on-disk)). A clone that shares entry objects (`cloneCurrentSession`, `captureState`/`restoreState`) keeps the store open as long as it needs it. `close()` closes the store at once unless a clone still holds it, a clone made with `persist: false` included, which lets go of it in its own `close()`; so close a manager last: an older entry of a closed manager cannot be read. A store a manager let go of otherwise (a switch to another session) closes once it is collected.

**When the store cannot be used.** Where the platform has no account id (Windows), and when no store file can be made under `os.tmpdir()` (read-only, full, missing and impossible to create, under a regular file, or its directory not one the account owns alone), the store keeps its records in memory instead, compressed with zstd (level 3) in blocks of whole records of at most 1 MiB, a larger record in a block of its own; the records still being gathered for the next block stay as bytes. A read of a record in a block decompresses that block, and the reads after it in the same synchronous pass (a full rewrite, a walk over every entry) share it while they stay in that block, so a pass over the records in store order decompresses each block once. The block is dropped as soon as the pass ends (in a microtask): what stays is the parsed record in the cache below, so a read keeps no whole body or block past its pass. The entries go cold exactly as with a file, with the same records, and no other directory is used. Measured on a 361 MB transcript resumed this way, 328.5 MiB of records took 63.4 MiB (0.193 of their size), so the older bodies take about a quarter of their size in memory or less, and on two others a read of one record took 1.6 to 2.0 ms. When a write to the store file fails later (a full disk), the records that write held and every later one go to compressed blocks the same way, and the store tries no write again; the records already in the file are read from it. When an entry's images cannot be written to the blob store as it goes cold (a full disk), or the entry nests deeper than the walk that replaces its images recurses, its record is the entry's JSON with the images inline, written by a writer that keeps its own stack where `JSON.stringify` runs out (Bun's stops near 40,000 levels; a transcript line can nest 400,000), and the entry goes cold as any other. Only a value JSON cannot write (a cycle, a getter or `toJSON` that throws, a bigint in a value too deep for a recursive walk, a text longer than the engine's longest string) leaves an entry whole, and the next pass tries again; an entry parsed from a transcript holds none of these. A warning is logged, with the reason, the first time a process cannot make a store file (not where the platform has no account id, where it tries none), when a store's write fails, and the first time a store's entry stays whole because its record could not be made.

**What stays in memory before the cut, by kind.** These entries stay whole: every `custom` entry (extension and feature state) except `entry_patch` records, which hold the new bodies of the entries they patch, `session_exit` records (the arguments of the tool calls pending at an exit, of which a resume reads only the newest record's kind and count), `goal-completed` records (each holding a completed goal's objective, which the goal's `mode_change` entries hold too; nothing reads them back), `user_todo_edit` entries (a user's edit of the to-do list, each holding the whole list), `todo_hud_state` choices (each holding the list's JSON text), `experimental_context_notes` revisions and `tool_execution_start` markers (read only for the calls left pending at the end of the branch, after the cut); `model_change`, `thinking_level_change`, `service_tier_change`, `ttsr_injection`, `label`, `credential_pin`, `reset_boundary`, `model_usage` and `title_change` entries; the newest `session_init` on the current path; the newest canonical to-do snapshot on the current path, a `todo` tool result that records the list or a `user_todo_edit`, whichever is newer (what the to-do list restores from); the newest `todo_hud_state` and the newest `mode_change` on the current path (what a resume restores; a goal records a `mode_change` holding its objective every turn, and of an older one a resume reads only its mode and the approved plan file it names, which a cold `mode_change` keeps in memory); the notebook revisions every context build reads (the newest valid one after the last `/clear`, and any newer invalid one); and, for an `experimental-context-rollover` compaction the context starts from, the request its context takes from before the kept entries. Every other entry before the cut, or off the current branch, is **cold**. From the cut on, every `entry_patch`, `session_exit` and `goal-completed` record, a `user_todo_edit` that is not that newest snapshot, a `todo_hud_state` or `mode_change` older than the newest of its kind, and a compaction older than the oldest one a context build reads (the stale entry a snapcompact frame rescue replaces, which keeps its archive text) are cold too, since neither the model context nor a turn reads them; nothing elides them from the file.

**Cold entries.** A cold entry is the same object as before. Its `type`, `id`, `parentId`, `timestamp` and `activeLeafId`, its message's `role`, and every value that is small (a number, boolean, `null`, a string of at most 64 UTF-16 units, or an object or array whose JSON text is at most 320 bytes) stay ordinary properties. Larger values (message content, tool `details`, summaries, provider payloads) become enumerable accessors that read the entry's record back from the store on access, so `JSON.stringify`, spread and `structuredClone` still see every field. A cold message keeps as ordinary properties only the small values of the fields that readers walking the whole branch read on every turn: `role`, `timestamp`, `stopReason`, `provider`, `model`, `api`, `usage`, `responseId`, `toolCallId`, `toolName`, `isError`, `attribution`, `customType`, `display`, `errorMessage`, `prunedAt` and `useless`; every other field of the message (`content`, `details`, `requestControls`, `contextSnapshot`, `duration`, `ttft`, `completedAt`, …) is an accessor whatever its size. Of those fields, a string value of `toolCallId`, `responseId`, `provider`, `model`, `api`, `toolName` or `customType` that is not a blob reference stays an ordinary property whatever its length: these are identifiers a provider or a tool assigns, the per-turn readers key every message by them, and some run past 64 UTF-16 units (an OpenAI Responses tool call id is 81 characters). A cold `user_todo_edit` or `tool_execution_start` entry keeps only its `type`, `id`, `parentId`, `timestamp`, `activeLeafId`, `customType` and a small `runtime`; its `data` is an accessor however small. A cold `custom_message` also keeps, out of sight, whether it is a request a context-rollover compaction can take (a user's request, or the parent's IRC message, which only its `details` tell), decided as it went cold, so the walk that looks for that request on every context build reads no record back. A cold `mode_change` keeps, the same way, the approved plan file its `data` names (or that it names none), so a session's start, which walks the mode changes back to the newest plan mode for an approved plan, reads no record back for the goal mode changes a long goal session holds. The eight most recently read records are kept parsed for the next field read, at most 16 MiB together, each counted with its images resolved to their base64 data (a record in the store holds an image as a blob reference), but for snapcompact frames, which stay blob references in both and are read through `lazyImageDataSync` when a context build selects them. After every 16 MiB of records read back from the store, or written to it by a load, a full collection runs, so one loop over many older entries (an extension reading every message's content at a session start) or the load of a long transcript does not hold the garbage of every record it handled at once; reads served from memory never trigger one.

**Values read from a cold entry are frozen.** Writing into one throws a `TypeError` instead of losing the change. Assigning a field (`entry.message = …`, `message.content = …`) makes the whole entry whole again, and the assignment applies. To change nested values, call `sessionManager.updateEntryBody(id, entry => { … })`: it makes the entry whole, runs the update and returns the entry to the store with its new values; persist with `rewriteEntries()` as for any in-place update. A reader of the recent turns can use `getBranchFromCut()`, the branch from the cut to the leaf, whose bodies are all in memory except the records listed above as cold from the cut on, and `buildTranscriptSinceCompaction()`, the end of the display transcript from the newest compaction on the branch, which the retry check of an idle session reads.

**Load.** Resume, switch, reload, `continueRecent` and `forkFrom` stream the transcript: each entry is migrated and completed as it arrives. When the stream reaches a compaction, the entries before its kept start are written to the store, unless their kind stays whole; the entries since stay whole until a later compaction or the end of the stream decides, so a session with no compaction and no other branch writes nothing to the store. After the stream the entries the cut keeps whole are made whole, stale replay metadata is stripped from what any load-time pass left, every other entry still whole (off the leaf's branch, a record that is cold from the cut on, or one made whole by a pass or the stripping) goes to the store, and blob references of whole entries are resolved. A full write reads each cold entry's record once, one entry at a time, and writes the line the whole entry would give; its images stay blob references, so the write reads, hashes and stores none of them again.

**Diagnostics.** `sessionManager.coldStoreStats()` returns `{ coldEntries, storeBytes, materializations, hydrations, storeInMemory, compressedBytes }`: the entries whose large values are in the store, the bytes of records written, the records read back to serve a field read, the cold entries made whole again, whether the store keeps new records compressed in memory, and the bytes of its compressed blocks. `SessionManager.inMemory()` holds every entry; a copy of it that `persistCopy()` writes moves its older entries to a store as any persisted manager does.

## Storage Abstractions

`SessionStorage` owns filesystem-like operations used by `SessionManager`: synchronous directory/existence/write/stat/list operations; async read, sliced read, write, guarded atomic write, rename, unlink, artifact-aware deletion, title update, writer creation, and backend drain. Optional capabilities include synchronous reads, chunked reads (`readChunks`), streamed full writes (`writeLinesSync`, `writeLinesAtomic`), confirmed remote writes, assistant-turn scans, file locking, session ownership claims, and conditional artifact-aware deletion.

An `IndexedSessionStorage` backend (`SessionStorageBackend`, for an SDK's own store) implements `init`, `loadIndex`, `readFull`, `readSlices`, `writeFull`, `append`, `updateSessionTitle`, `truncate`, `remove`, and `move`, and may implement `readFrom`, `readChunks(path, fromByte)` (the stored bytes as chunks; rejects with ENOENT for a missing path), and `writeFullStream(path, chunks, byteLength, mtimeMs, title, expectedSize)` (a `writeFull` whose body arrives as UTF-8 chunks, with the same size check; a stream that fails or ends short replaces nothing). Without the last two, reads and full rewrites hold the whole transcript in memory: without `writeFullStream` a full rewrite hands `writeFull` the joined lines, and keeps no spool or compressed copy.

On indexed storage, the asynchronous writes of a path (`writeText`, `writeTextAtomic`, `writeLinesAtomic`, a title update, a rename or `renameNoReplace`, an unlink, `deleteSessionWithArtifacts`) take their places in one order per path when they are called, before their first await; a rename takes the places of both its paths at once, and `deleteSessionWithArtifacts` takes the places of the session path and of the artifact paths in the index at once when it is called. An artifact path indexed after that call is not ordered against the delete, which waits for the writes queued on it to settle and then removes it too. Each write goes to the backend only after every write called before it on any of its paths has settled. A write that fails, also one whose body cannot be prepared, fails only its own caller and lets no later write past those called before it. An atomic write prepares its body while the writes ahead of it settle. A synchronous write (`writeTextSync`, `writeLinesSync`, a writer's append) still queues at once. `drain` also waits for the asynchronous writes that have not queued anything yet.

Implementations and adapters:

- `FileSessionStorage`: real local files
- `MemorySessionStorage`: map/chunk-backed in-memory storage for non-persistent sessions and tests
- `IndexedSessionStorage`: shared local index plus ordered remote publication used by Redis/SQL-backed storage
- `SqlSessionStorage`: a PostgreSQL, MySQL, or SQLite session table (`omp_session_files`, created on first use) keyed by the same path string a file session would have, with each session's content in a `<table>_parts` table (see [SQL session storage](#sql-session-storage))

`SessionStorageWriter` exposes `append`, optional `appendSync`, `flush`, optional `flushSync`, `isOpen`, `close`, and `getError`.

### Selecting the storage

The root command (interactive, print, RPC and ACP modes, and `omp join`) resolves one process-wide default storage at start-up (`resolveSessionStorage` in `session-storage-config.ts`, installed with `setDefaultSessionStorage`) before it opens any session; every `SessionManager` factory, `resolveResumableSession`, the session picker, recent-session listing, the session archive's listing and lookup by id, and the subagent transcript discovery behind `/export` and `/dump all` fall back to `defaultSessionStorage()` when no storage is passed, so a session written to SQL is found by `--resume`, `--continue`, the picker, and the archive, and exports with its subagents, without a second path. `--export` and `omp share` read a session without reaching that install, so each resolves and installs the same storage itself first. `omp gc`'s blob sweep resolves `session.storage` the same way at maintenance time so it can discover a SQL-only session's blob references; its archive and WAL sweeps are unrelated to the transcript backend and stay on-disk-tree-only. The other subcommands never install the configured storage and still use the JSONL tree: `omp render` and session-id shell completion read sessions there, `omp stats` counts usage only from transcripts there (so SQL-stored sessions are not counted), and `omp cleanse` and `omp compress` write their own sessions there.

- `session.storage: file` (default) — the JSONL tree above; nothing is read or logged.
- `session.storage: sql` — read the file `session.sql.dsnFile` names, trim it, open it with `Bun.SQL` (dialect from the URL scheme: `postgres://`, `mysql://`, `sqlite:`), and `await SqlSessionStorage.create({ client })`, which creates its tables (migrating an older session table) and warms the index. `OMP_SESSION_STORAGE` and `OMP_SESSION_SQL_DSN_FILE` take precedence over both settings.
- SQL-backed sessions run subagents inline on the main thread until a session-storage service for workers exists; `task.workerThreads` does not offload their runs, follow-up turns, or revivals. File-backed sessions keep worker placement.
- For PostgreSQL and MySQL, an omp-created SQL client holds at most two connections and returns idle connections after five seconds. The next session operation reconnects if needed. This pool policy is built in; callers using `SqlSessionStorage` directly keep control of their own client.
- Resume takes the same value as today, `--resume=<session path>`: under SQL that string is the row's `path` key, and it embeds the home-relative sessions root, so the resuming process needs the same storage variables and the same home directory.
- Refusals (exit 1, message on stderr, never a fallback to files): `sql` with no file named anywhere names both `OMP_SESSION_SQL_DSN_FILE` and `session.sql.dsnFile`; a missing or unreadable file — `<source> names <path>, which could not be read: <reason>`; a blank file — `<source> names <path>, which is empty`; an unreachable database — `<source> names <path>, but the session database could not be opened: <driver error> (<code>)`, and when the server itself refused, `(<code> <SQLSTATE>)` with the five-character SQLSTATE it sent (`(ERR_POSTGRES_SERVER_ERROR 57P03)` for a PostgreSQL server that is starting up, `53300` for one with no connection slot left, `28P01` for a refused password; `(ERR_MYSQL_SERVER_ERROR 28000)` for a MySQL login refusal); any other storage value — `<source> is "<value>"; expected "file" or "sql"`. `<source>` is the variable or setting that supplied the value; the connection string itself is never printed.
- Tool artifacts and image blobs stay under the agent directory on local disk in either mode. Under `sql` the store also keeps each image blob a session references and cannot draw again (an image content block, an `images[]` entry, a provider `image_url`, a generated image) in `<table>_blobs`, and a session opened where the local blob store lacks one writes it back there from the table, so a session resumed on another machine keeps its images. Snapcompact frames are never stored in the table: a frame whose blob is missing is drawn again from its archive's text (`preserveData.snapcompact.text`) and used only when its bytes hash to its reference. `omp gc`'s WAL sweep keeps working on the on-disk tree; the blob sweep also reads a SQL-only session's transcript straight from the table so it never deletes a blob that transcript still references.
- Prompt history and the idle recap journal stay in the local `history.db` in either mode; neither enters the session store. A session journals its idle recaps there under `sql` as under files, so the `archive` prelude's prompt, search and recap views, the recaps its session views carry, and a resumed session's recap line show what this machine's sessions submitted and journaled.
- Joining a collab session (`/join`) needs file storage: the guest's replica of the host session is a local file, so under `sql` the join refuses with an error naming `session.storage` rather than resuming an empty session.
- The resume picker's F2 rename reads and writes the session through the configured storage, and first claims the session, holding the claim until the title is written: under file storage it takes the session's ownership lease, and under `sql` it waits for the database's answer to a claim (`acquireSessionClaim`). A session another process holds is left alone: the rename fails with a message that the session is in use by another omp process (the session this process has open) or that it is in use or no longer available (any other session). A storage that claims nothing, such as an SDK store built without `claims`, has no other holder to refuse for, so the rename does not check.
- These features work only on the JSONL tree. Under `sql` each refuses with `<feature> is unavailable with session.storage: sql: <reason>` instead of acting on an empty tree:
   - `omp gc --compress` (or `gc.compress`) and the background `gc.autoCompress` run compress session files in place on disk. `omp gc` skips the strip, compress and archive steps and runs the others; `gc.autoCompress` writes the refusal to `gc-auto-compress.log` and does not start.
   - `omp gc --strip` (or `gc.strip`) rewrites session files on disk to drop replay data. Selected by `gc.strip`, it is reported as not run; named with `--strip`, the refusal fails the run.
   - `omp gc --archive` (or `gc.archive`) gzips cold session files on disk and judges which sessions are cold from those files. Selected by `gc.archive`, it is reported as not run; named with `--archive`, the refusal fails the run.
   - `omp stats`, `/stats`, `/trace` and the `/usage` activity heatmap read session files. `/usage` still shows provider quotas.
   - `omp session lease` and RPC `get_session_lease` probe the file ownership lease, which a SQL-backed session never takes. `omp session pack`, `unpack`, and `moved` work only on session files on disk.
- `omp cleanse`, `omp compress` and session completion (`omp __complete sessions`) read the configured storage.
- The debug menu's "Clear artifact cache" removes tool output files (`<id>.<tool>.log`) older than 30 days from the sessions' artifacts directories, in both storages. Nothing else there is removed: not transcripts or their sidecars, subagent outputs, `/btw` conversations or drafts, and never a session or project directory. It does not follow a directory replaced by a symlink, and leaves a file replaced since it was listed.
- Resume forks a session that `omp session moved` marked as moved away (`forkIfMovedAway`). Only a session file can carry that mark, so a SQL-stored session always resumes in place.

### SQL session storage

`SqlSessionStorage` (`sql-session-storage.ts`) keeps sessions in PostgreSQL, MySQL/MariaDB, or SQLite through `bun:sql`, in four tables, and on PostgreSQL and MySQL a fifth:

- `<table>` (default `omp_session_files`): one row per session file with `path`, `content`, `mtime_ms`, the title fields, and `byte_len`, the session's size in UTF-8 bytes.
- `<table>_parts`: the session's content as parts keyed by (`path`, `start_offset`), where `start_offset` is the part's byte offset in the session.
- `<table>_blobs`: one row per blob a session references and cannot draw again, keyed by `sha256` (the SHA-256 of its bytes, as its `blob:sha256:` reference names it), with `content`, `byte_len`, `mime_type`, and `created_ms`, milliseconds since the epoch when the row was written.
   - **Written:** a blob is queued when persistence first puts it in the local blob store in a process. Its bytes must hash to its key, or it is never stored. It lands in a transaction of its own, `INSERT … ON CONFLICT (sha256) DO NOTHING` (MySQL `ON DUPLICATE KEY UPDATE sha256 = sha256`), under no session's write fence: the row is keyed by its content and never changes, so a lease another holder took does not stop it. A transcript write that names a queued blob waits for the lands already started, then for one land of its own, a pass over every queued blob in the order they were queued, and is rejected only for a blob it names that did not land, so no committed transcript names a blob the table lacks; a write naming no queued image waits for none. A blob write is tried three times (250 ms, then 500 ms apart), but on PostgreSQL a try whose 4 attempts all met a connection that no transaction can repair (see below) fails it at once and ends that land: the land tries no other queued blob, and each one it did not try fails with that error as its cause and stays queued. So on such connections each land closes at most 4 of them. Each image starts a land when it is queued and a transcript write starts one more, so a write that names n newly stored images closes at most 4(n + 1); one that finds k of the blobs it names gone and lands them again (see the races below) meets at most k + 1 more lands. A session open that writes m images back (see **Read** below) meets at most m + 1 lands, one for each image it queues and one for its reference rows, so it closes at most 4(m + 1) through lands; the transaction that writes its reference rows meets k + 1 more when it finds k of the blobs gone, as a transcript write does. Each of the open's other steps is an operation of its own and closes at most 4: each batch it reads (blob sizes, rows whose bytes do not hash to their key, blob bytes), each row it rewrites, and the transaction that writes its reference rows. On connections that are all repairless the open's first read, of the blobs' sizes, fails, so it queues no image, writes no reference rows, and closes 4. `drain()` is one land of its own, so it closes at most 4 more, however many blobs stay queued. A blob write that still fails stays queued, fails the transcript writes waiting for it (the session reports a persistence error), and is tried again by the next. Each new row logs its bytes (`Stored a session blob in the session database`).
   - **Large blobs:** a blob larger than one row takes is stored as parts, each a row under its own hash, and the row of its own hash lists the parts' keys, with `byte_len` the whole blob's. One row takes at most the `maxBlobBytes` option, default 512 MiB, and on MySQL and MariaDB at most the server's `max_allowed_packet` less 1 MiB (15 MiB under MariaDB's 16 MiB default, 63 MiB under MySQL 8's 64 MiB).
   - **Read:** at load, every referenced blob the local store lacks is read from the table in reads of at most 16 MiB (a larger blob alone), each written to the local store, with its display copy (`<hash>.png`), when its bytes hash to its key, before the next read; a row that does not is left out with a warning. Opening a session for writing also queues each referenced blob the local store holds and the table lacks (the queue stores no bytes that do not hash to their key), rewrites a row whose bytes do not hash to its key from this machine's bytes when they do, and then writes, under the session's write fence, the session's reference rows for every blob it names that the table holds. A session written before the reference table has none of its own until then, and its images reach the table only by this write-back, so without them a delete of another session naming the same image (a fork) would take the row.
   - **Deleted:** a session delete (`remove`, so `unlink`, `deleteSessionWithArtifacts`, the session picker's delete, `/tan` cleanup) and a move that replaces its destination delete, in the same transaction, the blob rows that no remaining reference names. `omp gc --blobs` also sweeps the table: it drops each reference of a path that has no session row, then deletes each blob row older than gc's write grace that no reference names and no transcript gc read names.
   - **Races:** every transaction that changes the session, blob or reference tables takes its locks in one order: (1) the lease rows of a fenced write; (2) session rows (and the parts under them), in path order, all locked before any of them changes, but for one key: a rename's destination that has no row (see the move below); (3) blob rows, in one pass in `sha256` order, parents and parts together; (4) reference rows. No statement after (3) takes a lock in the session table, and none after the first of (4) takes a blob row's lock the transaction does not hold. A transaction holds the row lock of every blob the references it inserts or deletes name before the first of them; a statement that deletes a path's references reads them first, without a lock, so their blobs are among those, and a delete reads a parted blob's part list the same way, so its parts are in the pass too. References are deleted and moved one key at a time: a delete or an update of a path's range (or a directory's, a scan) would lock on MySQL every row and gap it passes, and its inserts at another path could then wait for another transaction's range. On SQLite, which runs one write at a time, (2) takes nothing and (3) only reads which rows there are. `sql-session-storage-lock-order.test.ts` checks the statements of each kind of transaction against this order on every engine.
      - A transcript write takes its own session row (its insert or upsert, or its size check), then locks, shared, the rows of the blobs its content names; a full write, which replaces its path's references, also the rows of the blobs its current references name. Then it deletes the references its content no longer names (full write) and inserts its references. The write-back when a session opens takes no session row and does the rest as an append.
      - A session delete locks, exclusive and in path order, its session rows and, when it deletes a session with its artifacts, every row under the artifacts directory (on MySQL and MariaDB by the directory's key range, the one the delete of its parts uses, with the prefix compared as bytes too: the lock takes the rows of that range, the gaps between them and the gaps at its two ends, up to the nearest row outside it, which MariaDB locks too, and no other row, so an insert into one of those gaps, such as a rename's destination, waits for the delete; by the prefix compare alone, which can use no index, it would scan and lock every row and gap of the session table, and every other session's write on the database would wait for the delete), then deletes them; the directory's delete then finds the parts under the directory by their key range, on PostgreSQL only under a code-point collation (see the delete's bullet below). On MySQL and MariaDB a delete without the artifacts directory locks only the rows there are, found first by a read without a lock before its transaction (so the transaction's first read without a lock, which fixes its snapshot, comes after its locks), as it does blob rows: a locking read of a path with no row locks the index gap there, and an insert at another path in that gap (a rename's destination, a new session) would wait for it. It then locks, exclusive, the rows of the blobs the deleted sessions' references name and of their parts, then deletes those references and reads the remaining ones of those blobs. A move that replaces its destination locks both session rows (on MySQL and MariaDB those there are, read the same way) in path order before either changes, then does that for the destination, and in the same pass locks, shared, the rows of the blobs the moving session's references name, which then move; on MySQL and MariaDB it moves parts and references only when the source has some, since an update that finds no row locks a gap too.
      - A destination with no row is not locked before the move changes the source: on MySQL and MariaDB a lock of it would lock its gap, where two renames each waited to insert into the gap the other held. The move's `UPDATE` takes its key when it moves the source's row there, after the source's lock, so out of path order when the destination sorts first. A transaction that holds that key's gap and then waits for the source's row deadlocks with the move. One does: a delete with the artifacts directory, whose lock on MySQL and MariaDB takes, in path order, the rows and gaps of the directory's key range. It deadlocks with a move whose source is under the directory and whose destination lies in a gap of that range the delete reaches before the source: a path under the directory, or one such as `<stem>.k/s.jsonl` that sorts between the session's own file and `<stem>/`. The delete waits for the source's row holding that gap, or asking for it with the row, and the move's `UPDATE` waits for the gap. On MariaDB, which also locks the first row past the range, a move of that row into the gap just before it deadlocks the same way; MySQL locks only that gap, so there the delete does not wait. InnoDB rolls one of the two back, and the deadlock retry runs it again, so the end state is one of the two serial orders: the move first, then the delete; or the delete first, after which the move finds no source (`ENOENT`). A move of a row under the directory to a path out of the range does not deadlock: the delete waits for it, then leaves the row where the move put it. A move's source is under the directory when a move of the session itself carries it: under SQL storage `moveTo` carries the session's subagent transcripts and its unsent draft, rows keyed under its own artifacts directory, one rename each (`moveTranscriptTree`). A move into the gap after the directory from a source the delete does not lock waits at its `UPDATE` until the delete commits, and the delete waits for nothing. (`sql-session-storage-blobs.test.ts` expects one deadlock for a rename under the directory, for a source under the directory that moves into the gap just before it, under the directory or outside it, and, on MariaDB only, for a source that is the first row past the directory; shows a source past that first row waiting at its `UPDATE` into the gap after the directory while the delete waits for nothing; and shows the delete waiting, with no deadlock, for a source under the directory whose destination sorts past every row.) No other transaction does: the sweep locks no session row, a delete without the directory removes one path, so it waits for no second session row, and a write locks only its own. A destination another client creates after that read meets the `UPDATE` on the primary key (MySQL's 1062, PostgreSQL's 23505): `rename` then runs again, as many times as a deadlock's retry, and the next attempt locks the destination in path order and replaces it; past that it rejects with `SessionRenameRaceError`, changing nothing. `renameNoReplace` rejects with `EEXIST`.
      - The sweep drops each dangling reference with its blob's row locked exclusive, and locks no session row. On MySQL and MariaDB it locks the blobs' rows first, with no read before, and only then reads, without a lock, which paths have a session row and which of the references are still there: those reads fix the transaction's snapshot after the locks, so it holds every write that changed a reference to those blobs, as each takes the blob's row first. It drops only references it read whose path has no row; a write creating the path meanwhile waits for the blob's row and then references it again. (A lock on a dangling path's row, often one just deleted that InnoDB keeps delete-marked until purge, made a write creating the path wait in its insert's duplicate check; purge then turned that wait into a gap lock the write held, and two such writes in one gap deadlocked.) PostgreSQL's delete looks for the row again, without a lock. It deletes each candidate row with it locked exclusive.
      - A parted blob's insert takes its own row and its parts' rows in one pass in `sha256` order: its own row by its insert, each part locked shared where the table holds it (a part can be another blob's too), else inserted. Then it inserts the parts' references. A delete or a sweep of a parted blob locks its parts' rows in the same pass as its own.
      - On MySQL and MariaDB each of those locks is a statement of its own, one key each, in that order: the blob rows, the session rows of a delete and a move, and the delete's read of whether a reference to a blob remains (the first entry of that blob in the `sha256` index, with a shared lock). MySQL may plan a read of several keys of a small, changing table as a scan of the whole index, which waits for and locks every row it passes, rows of other keys too, and a read of several hashes, or of all of one hash's entries, locks next-key ranges into other blobs' entries. A blob's row lock alone keeps every reference to it from changing, since every transaction that adds, moves or deletes one takes that lock first.
      - So a delete that would take a row a write is referencing waits for the write's commit and then sees its reference (PostgreSQL reads at each statement's start; MySQL reads, one blob at a time, whether a reference remains, with a shared lock), and on MySQL and MariaDB no two of these transactions deadlock. A blob a full write stops naming goes with a delete of the last other session that names it.
      - A write that locks after a delete committed finds the row gone, lands the blob again from this machine's blob store, and writes once more.
- `<table>_refs`: one row per (`path`, `sha256`) where the session at `path` names the blob, written in the transcript write that names it (a full write replaces its path's rows) and when the session opens for writing, moved with the session, and deleted with it. A parted blob's parts are referenced from `blob:sha256:<hash>`, so no sweep takes a part of a kept blob. Its index `<table>_rhash` on `sha256` serves the delete's look; on PostgreSQL `create()` refuses to start when the table has no index led by `sha256` (on an expression or with a predicate does not count), whatever its name.
- The lease table (option `leaseTable`, default `omp_session_leases`): one row per claimed session with `session_id`, `holder` (a random token of the store that holds it), `host`, `pid`, `acquired_at`, and `heartbeat_at`, both times in milliseconds since the epoch on the database's clock. Rows are keyed by session id, and session ids are UUIDs, so stores with different session tables can share one lease table.

A session's content is its row's `content` followed by its parts in `start_offset` order. `content` is non-empty only on rows written before parts existed, until the session's next full write.

- An append is one transaction: it adds the line's byte length to `byte_len`, which takes the session row's lock, and inserts the line as a part at the old length. Concurrent writers serialize on that lock, and an append writes only the appended bytes. The lines a session queues while one of its appends is in flight go together in the next transaction (`appendBatch`): it checks the size once, adds their byte lengths to `byte_len`, and inserts them from the old length as parts of at most 1 MiB, short lines sharing a part and a longer line cut on UTF-8 character boundaries. When a statement of that transaction fails, so it rolled back before COMMIT, its lines run again one append each; when its COMMIT fails, they fail without running again, since the COMMIT may have landed.
- A full write (rewrite, size-checked replace, create-if-missing, truncate) is one transaction that locks the row, compares `byte_len` with the expected size, empties `content`, and replaces the parts with parts of at most 1 MiB split on UTF-8 character boundaries. No stored value grows past 1 MiB or the longest line appended alone, so sessions stay clear of PostgreSQL's 1 GB field limit.
- A session's full rewrite arrives as a stream (`writeFullStream`) and is staged: its parts, cut the same way, go in under the staging path `<path>#staging-<epoch ms, 13 digits>-<id>`, 16 parts per transaction, and one last transaction locks the row and checks `byte_len`, deletes the path's staging sets more than an hour old (which only a killed writer leaves), checks that the staging parts still hold every byte (a staging set another writer deleted is refused with `SessionWriteConflictError`), deletes the session's parts, renames the staging parts to the session (`UPDATE <table>_parts SET path = <path> WHERE path = <staging path>`), and sets the row's `content` to `''` and its `byte_len`. Staging parts have no session row, so no listing or index warm-up sees them. A failed write deletes its own staging parts. On MySQL, whose `path` columns hold 512 characters, a session whose staging path would not fit (a path of more than 473 characters) stages under `#omp-staging/<SHA-256 of the path, hex>#staging-<epoch ms>-<id>` (116 characters) instead, in the same way; that hashed prefix stands for the path's in everything below. Deleting a path deletes all of its staging sets, whatever their age, and a rename deletes those of the source and of a destination it replaces, each in the same transaction as the parts. These deletions are a primary-key range from the path's staging prefix (`<path>#staging-`, or its hashed form) up to an epoch (the cutoff, or the largest 13-digit one), which code-point and locale collations alike order by the epoch's digits, and so does MySQL's `utf8mb4_bin`, which compares as if the shorter string were padded with spaces (PAD SPACE): a staging name has a digit after `#staging-` and a `-` after its epoch, both above the space. The prefix is also compared exactly, whatever the `path` column's collation (on PostgreSQL as code points, on MySQL and MariaDB as bytes, as a session delete compares it, below), so a deletion never reaches another path's parts.
- Delete and rename remove or move the row and its parts, and delete the path's staging sets, in one transaction. Warming the index reads session rows only; a sliced read fetches only the bytes of the parts covering its head and tail windows, and a read from an offset (`readTextFrom`) only the session's size and the bytes of the parts covering `[offset, offset + maxBytes)`, each in one query whatever the part count.
- A whole read streams (`readChunks`): the row's own `content` from the read's offset when it has any, then the parts a page at a time by byte range (`start_offset >= <next> AND start_offset < <end> ORDER BY start_offset`), each part its own chunk. The first page spans 1 MiB from the read's offset, and each next one twice the last, up to 12 MiB; a page holds the parts that start within its span, so at most its span plus the part that starts last (the parts of a full write or a batch of appends are at most 1 MiB; a line appended alone is one part of its own length), and the first also the head of the part the read starts in. So a reader that stops within 1 MiB, as the Agent Hub roster's metadata read does after a transcript's first records, fetches about 1 MiB plus a part, and a session written one entry at a time reads in a few queries, not one per part. The read stops at the size its first query saw, so an append made meanwhile, which only adds parts past that size, is left out. A full write or delete replaces every part of the session, the one the read starts at included, so on PostgreSQL and SQLite the query of each page also checks, in the same statement, that this part still has the row identity the first query saw, and finds no parts when it does not: on PostgreSQL its `xmin`, the transaction that wrote it, which changes with every insert; on SQLite its rowid. SQLite gives a new row the largest rowid plus one, which after a delete, or a full write that leaves no part (a truncate), hands new parts the rowids of the deleted ones when those were the table's newest; so every part insert on SQLite (an append's, a staged part's, a full write's) takes a rowid above every rowid handed out before the current millisecond: the largest rowid plus one, or the time in milliseconds times 1024 when that is more, and a full write counts up from above the largest rowid it read before it deletes the parts it replaces. A part inserted in a later millisecond than a deleted one then never takes its rowid, unless the clock goes back (or, on a database file several hosts share, another host's clock is behind), a part is deleted and another inserted in the millisecond of the deleted part's own insert, or the table takes more than 1024 rowids a millisecond; a writer older than this rule still hands out the largest rowid plus one. A part whose rowid by this rule would pass 2^63 - 1, the largest SQLite has (as when another program stored a row under that rowid), goes in with no rowid of its own, and SQLite picks one as it does for an older writer: the largest rowid plus one, or, while the table holds rowid 2^63 - 1, an unused one at random; the rule then does not hold for that table. So on SQLite the query of each page also checks, in the same statement, that the last part already fetched is still at its offset with the same bytes. A replacement made between two pages within those bounds, by an older writer or in a table the rule does not hold for, can still reuse the rowid of the part the read started at and hold exactly the bytes of the last part fetched at its offset while it differs before and after it; a check at the read's end finds it. Before its first query a SQLite read takes `PRAGMA data_version`, which changes when any other connection, of this process or another, commits to the database file, and never for the connection's own commits (an in-memory database has no other connection, so a read of one takes no pragma); and two counts of the writes the store's client made: those to the path's slot (appends, full writes and the swap of a staged one, truncates, deletes, and both paths of a rename), and its directory deletes, one count per client that every read takes whatever its path, since a directory delete can remove any path. The slot counts are 1,024 hashed slots per client (a path's slot is `xxHash32(path) % 1024`), not one count per path, so a write to another path in the same slot, such as a parent session's append when its path shares a subagent transcript's slot, and a directory delete anywhere, whether or not the read's path is under it, cost that read extra check passes, at most two (the second when a count changes again during the first), and are never missed. At its end the read takes the pragma and the counts again; when any changed, it reads the bytes it yielded again, from its offset for exactly as many bytes, with the same page checks, and compares their SHA-256 with that of the bytes it yielded, so an append past those bytes is no conflict; when any changed again during that check pass (any other connection's commit to the database file changes the pragma), a write may have made it read the same mix again, so it reads them once more and accepts them only when that second check pass matches too: at most two check passes, and a pass that differs is a conflict at once. MySQL has no row identity. Its first query also takes, in the same statement and so from the same state as the size, the session's last part (the last one starting before the size): its start and the SHA-256 of its start, `:` and its bytes. When the read fetches the part at that start it must hold those bytes, and a read that ends must have fetched it, so any rewrite between two pages that grows, shifts or changes that last part is a read conflict, even a full write that grows the session past the old size, keeps the parts already read and has a part of its own end exactly there, which every page check passes. At its end one query computes a 128-bit digest of the bytes a read yielded (the row's own content from the read's offset, and the parts from the one the read started at up to the end of the last one it yielded, each whole) as the database holds them then, the XOR of the first 128 bits of each item's SHA-256 of its offset, `:` and its bytes, which the server aggregates (`SHA2`, `CONV`, `BIT_XOR`) without holding the session in memory; the read computes the same digest over what it fetched. Both checks run once the bytes a read yielded come from more than one query (the row's own content and a page, or two pages), when the read ends, and also when its reader stops early (leaves its loop after the bytes it wanted, as the advisor cost restore, the session listing's line scan and the Agent Hub roster do), so a stop never takes the start of one body and the rest of another for one transcript either. A page with no part where the read is, a part that does not start where the last one ended, parts that end short, yielded bytes on SQLite that are no longer all stored or hash otherwise, a last part on MySQL other than the one the first query saw, or a digest that differs, mean a full write or delete replaced the session during the read, and the read fails with `SessionReadConflictError` instead of returning a mix of two bodies (a reader that stopped early gets it from leaving its loop). Every reader of a stored transcript then reads it again from its start, up to three more times: a streamed load of a session (resume, a switch, a fork's source, the read before a claim), a copy of a transcript (the artifacts of a session that moves to a sibling, `omp render`), `omp gc --blobs`, the session listing's line scan, `peekSessionInit` (a parked subagent's revival), the continuation lookup's search for a turn (`holdsEntry`), the debug report bundle, the Agent Hub roster, the advisor cost restore, and memories stage 1, which reads a rollout from such a store in one streamed pass, so its head and tail come from one body. Each of them drops what it built from the failed read before it reads again. None reads it whole instead, and gc never skips it. What can go unseen on SQLite is a write made through the store's client by something other than the store, which neither the pragma nor the counts see; on MySQL, a replacement whose digest equals the read's, and a full write between two pages that keeps every part boundary up to the old size and the old last part byte for byte and differs only in same-length bytes of parts fetched after it, which the read then yields as the start of the new body, whole as far as it can tell. A digest of the whole read taken in the first query would see that case too, but every chunked read on MySQL, a probe that stops after its first page included, would then have the server hash the whole session: a probe of a 256 MiB session took 5,723 ms instead of 49 ms on MySQL 8.4. PostgreSQL and SQLite see that case, as every full write, by row identity.
- `moveTo()` refreshes the store before it checks the destination. A store that claims sessions claims the session the destination holds, and refuses when another live process holds it; a store that does not claim refuses a destination that holds any session, a copy of the moving session included, because another process may have it open. It moves the session and every row under its artifacts directory with a rename that never replaces (`renameNoReplace`): one `UPDATE … SET path` whose primary key rejects a destination row that exists, or that another client inserts during the move. The transaction then rolls back, the rows already moved go back (a key written at an old path since is kept, and the move reports the failed rollback), and the move fails with `SessionMoveRefusedError` naming the taken key. Redis storage does the same check, rename, mtime and title update in one script.
- Deleting a session removes its row and, in the same transaction, every row whose path starts with its artifacts directory (`substr(path, 1, n)`, so `%` and `_` stay literal) together with exactly those rows' parts, including rows another client committed after this client last refreshed. PostgreSQL (a `DELETE … RETURNING` feeding the parts `DELETE`) and MySQL (a multi-table `DELETE`) do it in one statement, so a child another client commits during the delete is either removed whole or kept whole; SQLite's `BEGIN IMMEDIATE` keeps every other writer out meanwhile. The same transaction then deletes every part under the directory that has no row: the staging parts of a staged full write whose writer was killed before its swap, of a path that may have no row at all (a subagent transcript whose first write was staged). MySQL finds them by a range of the parts' primary key, from the directory without its final `/` (`<stem>`) up to the directory with its final `/` made `0` (`<stem>0`). In code-point order every path under the directory (`<stem>/`) sorts within that range whatever follows the `/`, and so it does under `utf8mb4_bin`, which compares as if the shorter string were padded with spaces (PAD SPACE): there a path whose character after the `/` sorts below the space sorts below `<stem>/`, but still above `<stem>`. PostgreSQL takes the same range only when the `path` column's collation compares by code point: the builtin provider, and libc's `C` and `POSIX`. The store reads that collation once at start-up (the column's own, or the database's for the default collation). Under any other collation, ICU's included, a path under the directory can sort outside the range: a libc locale such as `en_US.UTF-8` ignores `/` at its first level, ICU's Thai collation ignores punctuation there (`'/s/a/b' < '/s/a0'` is false under `th-x-icu`), and any locale's tailoring, extension keywords or rules can do the same. PostgreSQL then compares the prefix alone, a scan of the parts table. Either way the prefix is compared exactly, whatever the `path` column's collation, so a part a row another client commits during the delete holds is not deleted; SQLite's delete takes every part under the directory. PostgreSQL compares that prefix, of the rows and of the parts, as code points (`substr(path, 1, n) COLLATE "C" = <dir>`): under a nondeterministic collation, such as a case-insensitive ICU one, `<stem>/` would otherwise equal a directory whose name differs only in letter case, and the delete would take that directory's sessions and the staging parts of a save under way there. SQLite compares the result of `substr` byte by byte (its `BINARY` collation) whatever the column's collation. MySQL and MariaDB compare that prefix, of the rows and of the parts, as bytes (`CAST(substr(path, 1, n) AS BINARY) = CAST(<dir> AS BINARY)`), which no collation orders: by `substr(path, 1, n) = <dir>` MariaDB 11.8 finds no path whose character after the directory sorts below the space, as a key range in PAD SPACE order would not. The session's own staging sets, which lie beside the directory, go by their primary-key range (`<path>#staging-` up to the largest epoch, which every collation orders by the epoch's digits). On MySQL the hashed staging sets of a path longer than 473 characters lie outside the directory's range: of the rows under the directory that the delete locks before any row goes (see "Races"), it takes those with a path that long, and deletes their staging sets, and those of the explicit paths that long, by their hashed prefix. A killed writer's hashed staging set of such a path that has no row is not found, and stays, as the staging set of a path never written again does. Redis finds and deletes the keys and their metadata in one script.
- A store built with `claims: true` claims the sessions it writes, so a second live omp process that opens one moves to a sibling with a new id instead of writing the same journal. The CLI always builds it so; an SDK store built from a client alone claims nothing, as before, and neither does an in-memory SQLite database. A claim's holder token is 128 random bits per store (never the host or the pid), always sent as a bound parameter.
   - On PostgreSQL and MySQL/MariaDB a claim is a lease row. The claim inserts it, or takes it over when its `heartbeat_at` is older than the expiry (30 s, option `lease.expiryMs`) on the database clock, or more than one expiry in the future (`heartbeat_at > now + 30000`, which a login that can write the table, or a clock jump, could leave; written as an addition because the column is a `bigint` and the subtraction form overflows), in one statement on PostgreSQL (`INSERT … ON CONFLICT … DO UPDATE … WHERE`, behind a transaction-scoped advisory lock keyed by the lease table and the session id, so the same session id in two lease tables takes two locks; the table's name goes into the key folded to lower case, as PostgreSQL resolves an unquoted name, so `omp_x` and `OMP_X`, one table, take one lock) and in a `SELECT … FOR UPDATE` transaction on MySQL/MariaDB. A claim waits for another transaction's lock of the row (the holder's write in flight) at most what is left of its caller's wait, or 5 s when the caller set none, and never through session state a pooled connection would carry to another client: PostgreSQL's `lock_timeout` for the claim's transaction; on MySQL 8 and MariaDB a `FOR UPDATE NOWAIT` read, and on MariaDB the insert of a new row as `SET STATEMENT innodb_lock_wait_timeout = <s> FOR INSERT …` (whole seconds, rounded up, at most what is left of the bound). A refused `NOWAIT` read throws its whole transaction away, and the claim runs again from its start until the bound has passed; nothing of the claim runs on in a transaction the refusal ended. That matters on MariaDB with `innodb_rollback_on_timeout` ON, where a refused `NOWAIT` read (error 1205) rolls back the whole transaction, not only the statement: a statement sent after it would run on its own, holding no lock (measured on MariaDB 11.4; MySQL 8's refusal, error 3572, rolls back only the statement either way). A takeover therefore waits for a write in flight that commits within that time, and sees it; a claim that waited that long is refused, the session held by the other process, never counted as this process's own, so the 35 s an open waits holds behind a holder stalled inside a write. A store that claims sessions needs MySQL 8.0 or later, or MariaDB 10.3 or later: on an older server (MySQL 5.7 has no `NOWAIT` and no statement-scoped lock wait) `create()` refuses to start, naming the server's version; a store without claims opens there as before. Start-up then runs each lock form it picked by that version, once, on the lease table and matching no row (`FOR SHARE NOWAIT` for MySQL 8; `LOCK IN SHARE MODE NOWAIT` and `SET STATEMENT` for MariaDB), and refuses to start, naming the version and the form, on a server that rejects one: a server that reports another family's version would otherwise fail every claim and fence. On PostgreSQL a store that claims sessions or makes its tables refuses to start on a server in recovery (a hot standby or a read replica, `pg_is_in_recovery()` read in the start-up look), naming that, instead of counting claims it cannot write as held; a store that does neither opens there, as before. The store refreshes, every 10 s (`lease.heartbeatMs`), the lease rows of the sessions it still holds a live claim on, by session id, and no other row of its, and deletes its row once the claim is released and the writes queued under it have landed; `drain()` waits for that, so a clean exit frees the session at once and a killed process's session is free 30 s after its last heartbeat. The database gives that delete up after 2 s (PostgreSQL's `statement_timeout` for the delete; on MySQL 8 and MariaDB a `FOR UPDATE NOWAIT` lock of the row first, the whole delete run again from its start while that lock is refused, for that long, so no session-level setting changes), and the store stops waiting 250 ms later if the database does not answer at all; the row then expires on its own, since the heartbeat no longer refreshes it. On MySQL and MariaDB the heartbeat is two statements in no transaction (an update, then a read that takes no lock), so a lock wait timeout fails that heartbeat alone. `SessionManager.close()` releases its claim only after its last publish, so every write of a closing session meets the fence.
   - **MySQL 8 only: one case waits past the claim's bound.** MySQL bounds no `INSERT`'s lock wait without session state: `SET_VAR` does not apply to `innodb_lock_wait_timeout`, and `MAX_EXECUTION_TIME` applies only to a `SELECT` (both measured on MySQL 8.4). The case is a claim that inserts a new lease row while a write is stalled inside its transaction, between its fence and its commit, where that write comes from a store with claims on writing a session it holds no claim on (a title change or a delete of another session). That write's fence holds InnoDB's share lock on the missing row's index gap (see the next item), and an insert into the gap waits for it. The gap can hold other sessions' new rows too: with time-ordered session ids, every session started after the one written. The claim's insert waits until the write commits or rolls back, or for the server's `innodb_lock_wait_timeout` (50 s by default). At worst that is an explicit resume's 35 s wait plus that timeout, 85 s with the defaults. A claim that sets no wait (the automatic resume, or a new session's first write) waits that timeout alone, and the writes queued under it wait with it. A timeout counts as held by the other process, as every lock timeout does, so the session moves to a sibling, or the process stops under `OMP_SESSION_EXCLUSIVE=1`. It is safe: the insert lands only after the stalled write has ended, so a write whose fence found no fresh lease never lands after the claim, and two writers never share a session. MariaDB bounds the insert (`SET STATEMENT`) and PostgreSQL bounds the claim (`lock_timeout`). A store without claims, and an older omp, run no fence and take no lease lock, so they never make a claim wait.
   - Every content write (append, full write, each transaction of a staged full write (each batch of staging parts, the swap, which also deletes stale staging sets, and the delete of its own staging parts after a failure), truncate, title update, delete, both paths of a rename, and every marker write, such as the draft-only marker and the draft under a session's artifacts directory) first reads, in the write's own transaction, the lease row of the session it writes: for a path this store claimed, its own row, share-locked (`FOR SHARE` on PostgreSQL, `FOR SHARE NOWAIT` on MySQL 8, `LOCK IN SHARE MODE NOWAIT` on MariaDB), refusing with `SessionLeaseLostError`, changing nothing, when the row is gone or names another holder; for any other path of a session (its file, or anything under its artifacts directory, by the `<time stamp>_<id>` name), refusing while another holder's lease of that session is fresh, after taking a shared lock a claim of that session waits for (on PostgreSQL the session's advisory lock, shared; on MySQL/MariaDB the share lock of the missing row's gap), so a claim made while such a write is open lands after it. A fence waits at most 2 s for another transaction's lock (a takeover in flight), then refuses the write the same way; on MySQL and MariaDB a refused fence read throws the write's whole transaction away and the write runs again from its start within those 2 s, so no statement of the write runs after a refusal in the transaction it ended (see the claim above for MariaDB's `innodb_rollback_on_timeout`); on PostgreSQL that bound covers the fence statements alone (`SET LOCAL lock_timeout = 2000` before them, `SET LOCAL lock_timeout TO DEFAULT` after them), so the write that follows waits as the login, the database and the server set `lock_timeout`. On PostgreSQL the server ends a heartbeat transaction that stops for 500 ms while it holds its row lock (see "On PostgreSQL the store runs no code another login planted" below), so a fence waits on the store's own heartbeat for less than its 2 s bound. A takeover's update of a row waits for a write in flight to commit, so the new holder sees it, and the old holder's later writes are refused. A takeover, a refused write, or a heartbeat that finds the row gone or another holder's marks the claim lost (only a release deletes a row, so a gone row means another holder came, wrote and released): `SessionManager` moves the session to a sibling at once and writes its whole transcript there, the refused entries included.
   - A subagent transcript under a session's artifacts directory (`<stem>/<agent>.jsonl`) is claimed under that session's lease, never under an id of its own. When the session's lease is lost and the session moves to a sibling in the same process, the transcript follows it: it moves to the same relative path under the sibling's artifacts directory once the session's artifacts are copied there, keeps its id, and publishes its whole transcript there. The process remembers such a move only while the manager that made it still runs that session: once it closes, or opens or starts another, the move is forgotten, and a transcript of the old session whose lease is lost later forks instead of following into the abandoned sibling. When the session is another process's (it holds the lease, or took it over and went on elsewhere), nothing records where it went, so the transcript forks to a session of its own beside the session's file, under a lease it takes there, whose header names the session as `parentSession` and carries no `continuationOf`, and publishes its whole transcript there, so no entry is lost. This happens under `OMP_SESSION_EXCLUSIVE=1` too: a subagent transcript's id is never the launcher's recorded one. An `OMP_SESSION_EXCLUSIVE=1` stop asks the store who holds the session for at most 2 s, so a database that stopped answering still lets the process end, without the holder's name.
   - A store that claims sessions also refuses an append onto bytes it did not write: another writer that claims nothing, such as an older omp, changed or replaced the file. `SessionManager` then reads the file back once its own queued writes have settled, keeps the other writer's new entries and publishes the whole transcript again, or moves to a sibling: `replaced` when the file now holds another session, `contested` after repeated conflicts. A read-back that another writer's full write cut off (`SessionReadConflictError`) is read again, at most three reads in all, before the session moves to a sibling as `contested`. A full publish it queued itself (a `flushSync` publish the store confirms later) that meets such a change recovers the same way. A rewrite a caller asks for (`rewriteEntries()`) was computed from a stale view, so it still rejects with `SessionWriteConflictError` and changes nothing, on SQL as on Redis; the caller retries from a fresh load. Under `OMP_SESSION_EXCLUSIVE=1` either move ends the process non-zero instead, naming the reason.
   - A claim whose heartbeats the database has not answered for 20 s (the expiry less one interval, counted from when the last answered heartbeat was sent, however late its answer came) lapses: its writes wait, up to one expiry, for the next answered heartbeat, and nothing moves. When the database is reachable again, a heartbeat that finds the row still the store's confirms the claim; only another holder makes it lost.
   - An explicit resume (`--resume`, the session `--continue` picks, the picker's pick, and a switch, which RPC `open_session` and `switch_session` go through) takes its lease before `session_start`, waiting up to 35 s (the expiry and 5 s) for another holder's to go or expire, saying so on stderr; then it claims it and keeps the id, or moves to a new id if it is still held. The automatic resume claims the session it picks before `session_start` too, but does not wait: a start that names no session and picks none, with no `--resume` and no `--continue`, never waits, so a held session moves to a new id at once. A switch takes the lease before the manager takes the new id, so while it waits the manager still reports the session it had. After each acquire the manager reads the session again when its stored `byte_len` is not what it last loaded or wrote.
   - A move to a sibling is a fork: the sibling's header names the old id as `parentSession` and carries no `continuationOf`, so nothing points a later resume of the old id at it. An exact `--resume <id>` opens exactly that session and follows no continuation an older build recorded; the picker, `/resume` and a `--resume` prefix still follow one.
   - Under `OMP_SESSION_EXCLUSIVE=1`, which a launcher sets when it passes a recorded id, nothing moves the id: a session another process still holds after the wait, a lease taken over or gone, and a file another writer changed or replaced each end the process non-zero, naming the reason (and, for a lease, the holder's host and pid), and write no sibling, fork or continuation. After that stop the session writes nothing more, its own file included, while the stop waits (up to 2 s) to name the holder, and a `close()` in that wait (a signal's teardown) publishes nothing either, even with a write failure latched: a full write to its file, checked only against the size it last loaded, would land over the holder's bytes where no lease fence refuses it (SQLite) whenever the holder's file still had that size. In that wait, `flush()`, `flushSync()` and `close()` reject with `SessionExclusiveStopError`, once the stop line is on stderr, while storage does not hold every entry (the turn whose write met the stop's cause, or one appended after the stop, which the seal drops), so no caller takes an unsaved turn for saved; a stop that left every entry stored lets them resolve, and a dispose records no exit marker for it. A switch the stop comes before or during rejects with `SessionExclusiveStopError` and opens no other session, so the stop is judged against the session that stopped: the switch first lets a queued write's conflict recovery of that session end, gives up nothing of it once it stopped (its claim included), and `AgentSession.switchSession` keeps the manager's entries after the rejection. RPC and print mode end such a run with exit 1 and the stop line, without a crash dump. A resume of such a session follows no continuation either. A `departed` entry (`omp session moved`, or one another process appended) neither forks nor stops it: the start logs the entry, naming it, and opens the session itself, writing its next turn there. So two processes can run one session id after `omp session moved`; stop the pod before moving its recorded session.
   - A write the lease fence refuses after a main session was sealed (a dispose's `close()`) is that close's failure: under `OMP_SESSION_EXCLUSIVE=1` the session stops and `close()` rejects with `SessionExclusiveStopError`; otherwise the session moves to a sibling that holds the entries, as an unsealed session does, and `close()` waits for the copy of its artifacts and subagent transcripts there. A sealed subagent transcript (a file under its parent's folder) takes no part: its claim is its parent's lease, so its close neither moves it nor stops the process, and the entries a refused write of it carried are lost, as before.
   - After such a stop, a stopped work pool's discard records for a session the stopped session left are refused (`appendCustomEntriesToSession` resolves `"refused"` and writes nothing): nothing of this session writes after the stop.
   - A process stopped by SIGTERM or SIGINT gives its lease rows back before it exits 143 or 130. A running session is disposed by its mode's signal teardown (RPC, `--mode rpc` and `rpc-ui`, and print mode in the tests; interactive and ACP register the same kind of teardown): `session_shutdown` runs and the session manager closes, which releases the claim after its last publish and deletes the lease row. What no session teardown reaches, the store gives back itself: a signal earlier in startup, while extension modules load or their factories run and no mode's teardown exists yet, and a claim whose own release a signal skips (a subagent's, a delete's, a rename's, a move destination's). While a SQL store holds a lease row it registers an exit release with postmortem that starts only once every other cleanup callback of the pass has settled (`afterOthers`), so a mode's teardown runs `session_shutdown` and writes the exit entry under the lease first (an extension counting the row 1 s into `session_shutdown` finds it). That release waits for the writes already handed to the store, as every release does, then deletes each row the store still holds within the release bound, and logs one that fails or gets no answer; entries a session manager holds but never handed to the store are not written, as before. The release has that bound (2.25 s) as its own postmortem `deadlineMs`: when another cleanup callback's `deadlineMs` holds the pass open past postmortem's 10 s deadline (a login refresh that is still saving, an isolated task's cleanup), the release starts once that callback settles and still gets its time. When another callback never settles, or outlasts its own `deadlineMs`, the release does not start, since a mode's dispose still running could then write after it: the row stays and expires, 30 s after its last heartbeat. The next resume, an `OMP_SESSION_EXCLUSIVE=1` one included, then opens the session without waiting on a lease (no row left at the stop and no lease-wait line, in runs on PostgreSQL, MySQL 8.4 and MariaDB 11.4 with the signal while the session ran, during a slow `session_start`, and while an extension's module top level or async factory was still running, in RPC and print mode; it waited about 30 s before). When the database does not answer at the signal, the row stays either way: a teardown that waits on the database holds the pass to postmortem's 10 s cleanup deadline, which logs `Cleanup deadline exceeded; proceeding with exit`, and the process exits just after it (10.1 to 11.3 s after the signal in those runs); when no teardown waits on it, the release starts at once, gives up at its own bound and logs that, and the process exits then (2.4 s after the signal in one run). The next resume takes the row over once it expired, 30 s after its last heartbeat on the database clock (30.0 to 30.9 s in those runs). A process that runs nothing at exit (SIGKILL, a lost machine) leaves its row to expire the same way, and so does an interactive session's second Ctrl+C while its shutdown is stuck: that hard abort exits at once without postmortem's cleanup, since the step it cuts short is the session's own dispose, the same rule as a cleanup callback that never settles. A launch that ends by an exit of its own once it holds its session's lease (an unknown flag, no usable model, an `@file` that does not exist, a usage error found after startup, `--api-key` without a model, Ctrl+C twice or Ctrl+D on an empty draft in the startup composer before the session runs, the TUI debug socket's `quit`) exits through postmortem's cleanup (`postmortem.exitAfterCleanup`), so the store gives the row back first, as it does at a signal; RPC mode's exits after it disposes its session and an extension's shutdown in print mode do the same. An `OMP_SESSION_EXCLUSIVE=1` stop gives back the claims its store still holds (a subagent's) before it exits, within the release bound, and runs nothing else. A startup pick (`omp --resume` with `autoResume` on, where the launch first resumes its directory's most recent session on its own) closes that session once the picked one holds its claim, so its lease goes back and another process opens it at once; a pick of that same session keeps it, with its id and its claim.
   - On a SQLite file the claim is an OS lock keyed by the database file's identity, its device and inode (so a symlink, a hard link, or another mount of the file meets the same lock), and the session id; the kernel drops it when its process dies. It needs no lease row, no heartbeat, and no fence (`BEGIN IMMEDIATE` keeps every other writer out). The claim of a session being opened (`acquireSessionClaim`) that finds the lock held by another process keeps trying it until 50 ms after it began, so a session whose holder is letting it go is taken rather than moved to a sibling; it waits about that long at most for a live holder. The native claim of a held lock answers at once, so the store tries again every 5 ms.
   - Every claim checks first that the path holds no other session's header; a path that does is not claimed.
   - File storage claims a session at its first write, as before, except an `OMP_SESSION_EXCLUSIVE=1` resume, which claims it at open (see the file storage lease above); SQL storage claims an opened session before the agent session starts, so a second process never runs under the held id.
- PostgreSQL and MySQL run a write again, up to five attempts, when the database aborts it as a deadlock victim, and MariaDB when it aborts it as a write conflict too: error 1020 (`ER_CHECKREAD`, "Record has changed since last read"), which MariaDB raises under `innodb_snapshot_isolation` (on by default from 11.6.2) when a transaction's locking read or write meets a row changed after its read view was made, and which it rolls back as it does a deadlock victim. Each attempt recomputes everything under its own locks. On MySQL a full write deletes a session's parts, and every write that deletes staging sets deletes them, only after a non-locking look finds some, so creating sessions at once takes no gap locks.
- On PostgreSQL the store runs every statement in a transaction that it opens itself, on one connection that it reserves from the client's pool (`reserve()`): each table-setup statement at start, every read (each query of a streamed whole read, `readChunks`, too), an append, a full write, each transaction of a staged full write (`writeFullStream`), a title update, a delete, a rename, and each lease statement. The first message of each transaction is its opening, one simple query that the store builds from the list in `src/session/sql-session-postgres-settings.ts`: `BEGIN ISOLATION LEVEL READ COMMITTED READ WRITE` (`READ ONLY` for a read), `SET LOCAL application_name = 'omp-session-store'`, then a `SET LOCAL` of each other setting that a statement of the store depends on. Most of them, `role` included, go back `TO DEFAULT`; `client_encoding` is set to `UTF8`, `bytea_output` to `hex`, `synchronous_commit` to `on` and `search_path` to `pg_catalog, pg_temp`. Another client of a transaction-mode pooler, such as PgBouncer, can leave any session setting on a pooled connection. The opening sets each one back for its own transaction alone, so nothing of it stays on the connection. `TO DEFAULT` gives the value that the login, the database and the server set, so a limit that an operator sets for the login still applies. A setting that the caller set with `SET` on the client it gives the store, `SET ROLE` included, therefore no longer applies to the store's transactions, and a store that relied on `SET ROLE` runs as the login: give a setting that the opening sets back `TO DEFAULT` with `ALTER ROLE ... SET` or `ALTER DATABASE ... SET`, or as a start parameter of a direct connection. That does not work for the five that the opening sets to the store's own value, `application_name`, `bytea_output`, `client_encoding`, `search_path` and `synchronous_commit`: each transaction of the store runs with that value whatever the login, the database or the connection sets. After the opening the store sends its own bounds (the claim's `lock_timeout`, the release's `statement_timeout`, the fence's `lock_timeout`, the heartbeat's two bounds), its statements, and `COMMIT` or `ROLLBACK` itself.
- Each PostgreSQL write then reads `setting` and `reset_val` of `default_transaction_read_only` in `pg_settings`. `setting` is the session's own value, which the opening's `READ WRITE` does not change. `reset_val` is the default the session started from, which a session's `SET` does not change. A read-only value that a session set over a default that is off (`SET default_transaction_read_only = on`, or `SET SESSION CHARACTERISTICS AS TRANSACTION READ ONLY`) makes `setting` `on` and leaves `reset_val` `off`, and the opening's `READ WRITE` overrides it. The store still writes on that connection, the `CREATE TABLE IF NOT EXISTS` at start included. A read-only default that the database, the role, the server or the backend connection's start parameters set, and that the session keeps, makes both `on`, and the store honours it: it refuses the write before it changes anything, with an error that names `default_transaction_read_only`. An operator, or a provider that makes a database read-only when its disk is nearly full, therefore stops the store's writes. A session that turned such a default off has `setting` `off` and `reset_val` `on`, and the store writes there, as older releases did. A transaction-mode pooler applies a client's start parameters and its `connect_query` to the backend as session `SET`s, so the store overrides them like any session value and does not honour them. A read costs three round trips (the opening, the read, `COMMIT`) where it cost one. An append of a store that claims nothing costs four (the opening, the `pg_settings` read, the append statement, `COMMIT`) where it cost six. On a store that claims its sessions, as the CLI's does, the fence adds three (`SET LOCAL lock_timeout`, the read of the lease row, `SET LOCAL lock_timeout TO DEFAULT`), and the read of the session's size one more when the append checks it, so an append costs seven or eight round trips where it cost nine or ten. MySQL and SQLite do not do this, so a MySQL connection whose session default is read-only still refuses the store's writes.
- Each PostgreSQL transaction of the store shows `application_name` `omp-session-store` while it is open, in `pg_stat_activity` and on the lines it writes to the server log after its opening.
- On a PostgreSQL connection that no transaction can repair, the store closes the connection and runs the operation again on a new one, at most 3 more times. Such a connection refuses the opening (with `cloudsql_session_read_only = locked`, which another client can leave on Cloud SQL, it refuses with `25006`), ends before the opening's answer, or refuses a later statement with `25006` (read-only) or `42501` (insufficient privilege): the opening already set the role and the read-only settings back, so the session itself cannot write there. The store sends no `ROLLBACK` there, so the pool closes the server connection. It writes one warning line for each close, with the operation, the SQLSTATE, the server's message and the attempt. A login that lacks a grant therefore fails each operation after 4 attempts and 4 warning lines. A connection that ends after the opening's answer ends that operation with its error, and the store does not run it again, because it cannot know whether the work committed.
- A PostgreSQL client must have `reserve()`, which `Bun.SQL` has. A wrapper's `reserve()` must give back one real connection of its pool. On PostgreSQL `create()` refuses a client without `reserve()`, naming it, before it sends anything. A MySQL or SQLite client needs no `reserve()`.
- The store needs PostgreSQL 16 or later: the opening names settings that PostgreSQL 16 added, such as `debug_parallel_query` and `enable_presorted_aggregate`. On an older server, the first opening of `create()` is refused with `42704`, naming the first setting that the server lacks. The store closes that connection and tries again 3 times, and `create()` then fails with that error.
- At start the store reads, in a read-only transaction, which of the settings that some supported server lacks this server has (`restrict_nonsystem_relation_kind`, from PostgreSQL 16.4, `transaction_timeout`, from PostgreSQL 17, and Cloud SQL's own, such as `cloudsql_session_read_only`). Every later opening adds a `SET LOCAL` of each one the server has. Where the server has `transaction_timeout`, the opening sets it to `0` and then back `TO DEFAULT`, so the transaction runs with the default. `BEGIN` starts the transaction's timer with the value the session holds, which may be one another client left, and a later `SET LOCAL` stops a running timer only when the new value is `0`: `TO DEFAULT` alone, with a positive default such as `10min` for the login, would leave a shorter left value's timer running, and it would end the transaction and the connection with `25P04`. That first opening sets none of them back, so on PostgreSQL 17 or later a `transaction_timeout` that another client left can end it, and that `create()` fails once with the server's error. The timeout also ends that server connection, so the next `create()` meets another one. A `restrict_nonsystem_relation_kind` that another client left does not stop that read, since `pg_catalog.pg_settings` is a system view.
- On PostgreSQL start-up first looks, in one read and outside any lock, at which of its tables exist; that read also takes `default_transaction_read_only`'s `setting` and `reset_val`, and refuses to start on a read-only default the session keeps, as a write does. When all of them exist, start-up takes no lock and makes nothing. Otherwise one transaction makes them: after the `pg_settings` read it takes a transaction-scoped advisory lock (`pg_advisory_xact_lock`) with the store's fixed key `0x6f6d705f73657373`, decimal 8029197265931694963, looks again under it, and makes, in one round trip, each table still missing, with the `holder` index when it makes the lease table. `pg_locks` lists that lock as an `advisory` lock with `classid` 1869443167 and `objid` 1936028531, the key's high and low 32 bits. The lock ends with the transaction. Each later start-up statement (a missing column's `ALTER`, the `byte_len` backfill, the `holder` index on a lease table that was there without one) runs in its own such transaction. Stores that start at the same moment on a database without the tables therefore take turns, instead of failing with `duplicate key value violates unique constraint` or `already exists`, and stores that start on made tables never wait on one another. The opening's `READ COMMITTED` keeps a `repeatable read` default from failing the `byte_len` backfill with a serialization error after the lock wait. A store from an older Oh My Pi takes no lock, so it can still collide with a new one on such a database.
- On SQLite every store in a process runs one call at a time per database file, across all the clients of that file (keyed by the file's device and inode, so a symlink or a hard link to it shares the queue; a file that does not exist yet is created empty first, which SQLite reads as an empty database; in-memory databases, and wrappers that do not pass `options` through, queue per client), and opens every write with `BEGIN IMMEDIATE`. Clients of one file in one process therefore take turns and never wait on each other. When a client has no busy timeout, the store sets 5 s: a write then waits for another process's write lock, and if the lock is not released in time it fails at `BEGIN`, before changing anything. Keep your own transactions off a client the store uses: Bun runs each client on one connection, so the store's statements would join them.
- Deleting a session through `SessionManager` (`/delete`, the picker) on a store that claims sessions first claims it, waiting for the database, and refuses while another live process holds it.
- Table names are limited to 57 characters, so `<table>_parts`, `<table>_blobs`, `<table>_refs` and the index `<table>_rhash` stay within the 63-character identifier limit, and the lease table's name to 56, so its index `<leaseTable>_holder` does.

With `createTable` on (the default), `create()` creates the tables when missing, the lease table and its `holder` index on PostgreSQL and MySQL included, whether or not the store claims; on PostgreSQL it looks in `pg_index` for an index of the lease table keyed by `holder` alone, under any name, and creates `<leaseTable>_holder` only when there is none and nothing else holds that name. On a session table from an older Oh My Pi it adds `byte_len`, backfills it from each row's `content` where it is null, and creates `<table>_parts`. Stop every older Oh My Pi process that writes the table before the first upgraded one starts: an older version appends to `content` without updating `byte_len`.

With `createTable: false`, `create()` runs no DDL and refuses to start, naming what is missing, until the session table has `byte_len` and `<table>_parts`, `<table>_blobs` and `<table>_refs` exist, and, for a store that claims on PostgreSQL or MySQL, until the lease table exists; it also refuses while any row's `byte_len` is null. A store that does not claim never reads the lease table and needs none. Apply the schema in your own migration, substituting your table names for `omp_session_files` and `omp_session_leases`. A new database creates the session table with `byte_len`; an existing session table adds the column and backfills it. Both then create the parts table, the blob table, the reference table with its index, and the lease table.

A PostgreSQL login that owns none of the tables, such as one the tables' owner granted row access to, can open the store with `createTable` on once the tables and the indexes exist: every statement `create()` then runs is a read of the catalogs (it looks for the tables first and makes none that exists, so it needs no `CREATE` on the schema), or a statement it skips after looking (a missing column's `ALTER`, the `byte_len` backfill when no row lacks it, and the `holder` index, which PostgreSQL refuses to anyone but the table's owner even with `IF NOT EXISTS`). On the lease table the login needs `SELECT`, `INSERT`, `UPDATE` and `DELETE`: the fence's `FOR SHARE` needs `SELECT` and `UPDATE`, the claim's `INSERT … ON CONFLICT … DO UPDATE … RETURNING` needs `SELECT`, `INSERT` and `UPDATE`, and the release's `DELETE … WHERE` needs `SELECT` and `DELETE` (measured on PostgreSQL 16). The blob and reference tables need `SELECT`, `INSERT`, `UPDATE` (a repair, a move, and the row locks of a reference write and of a delete) and `DELETE`. Start-up refuses, on every engine, a blob table without its `sha256` primary key or a reference table without its (`path`, `sha256`) key, which their inserts' `ON CONFLICT` name; on PostgreSQL it also refuses one this login lacks one of those privileges on (`has_table_privilege`), and on MySQL one where a statement that changes no row and needs the privilege (`INSERT … SELECT … WHERE 1 = 0`, `UPDATE … WHERE 1 = 0`, `DELETE … WHERE 1 = 0`) is refused. On MySQL the lease table's index and the reference table's are part of their `CREATE TABLE`, so they add no statement there; a MySQL user needs `SELECT`, `INSERT`, `UPDATE`, `DELETE` and `CREATE` on each of the five tables, since `CREATE TABLE IF NOT EXISTS` needs `CREATE` even when the table exists (measured on MySQL 8.4).

On PostgreSQL the store runs no code another login planted:

- Every transaction it opens sets `search_path` to `pg_catalog, pg_temp` in its opening (`SET LOCAL`), and every read runs in such a transaction, with its values bound as parameters. The lease heartbeat runs in a read-write transaction from its first try, as every write does: after the opening and the read-only check it sets `lock_timeout` and `idle_in_transaction_session_timeout` to 500 ms with `SET LOCAL`, both below the write fence's 2 s bound, then sends its update, with the holder token and the session ids bound, and `COMMIT`. Its row locks may therefore last through one COMMIT round trip, but the server ends a stalled transaction before that fence can mark the claim lost. A heartbeat whose transaction the server ends, or whose COMMIT answer the store loses, is a failed heartbeat: the store does not run it again, and the claim stays as it was until a later database answer proves it held or lost. Every statement names the store's tables as `public.<table>`, whatever the login's `search_path` names, so a login whose `search_path` starts with another schema meets new tables in `public`, not the ones in that schema. A function or operator another login made in `public`, an exact match for argument types where `pg_catalog` has only a match through an implicit cast (`*(numeric, integer)`, `convert_to(text, text)`, `=(oid, regclass)`), is then never picked. The connection sets nothing at start-up: PgBouncer before 1.26, in transaction mode, refuses a `search_path` startup parameter, and `SET LOCAL` ends with the transaction, so a transaction-mode pooler passes nothing on.
- `create()` refuses to start, naming the table and what it found, when one of its tables has a column the DDL below does not declare, a column of another type than declared (a type of the planter's own, whose assignment cast would run its function, is found through `pg_cast`, not the search path), a column default, a generated or identity column, a trigger, a rule, row-level security or a policy, a constraint other than a primary key, unique or not-null one, an index on an expression or with a predicate, a table inheriting from it, or is not an ordinary table; when one of its tables is a partition or an inheritance child of another table (any `pg_inherits` row with the table as `inhrelid`, or `relispartition` alone), naming the parent, since every insert into a partition checks the partition constraint and so runs the parent's partition key, a function of whoever made the parent, as the store's login; when another table has a foreign key that references one of its tables (a `pg_constraint` row with the table as `confrelid`), naming that table, since the store's deletes and updates fire the key's referential action on that table, and with it that table's triggers; and when the lease table has no index keyed by `holder`, or the name `<leaseTable>_holder` is held by anything but such an index (an index of another table, or a table, under that name would make `CREATE INDEX IF NOT EXISTS` skip). This runs whatever `createTable` is. The store refuses every other column, not only one it would have to fill: an insert leaves the rest to their defaults, which it cannot vet without parsing them, and it reads none of them. The store declares no foreign key of its own.
   - A domain over a column's type (its `CHECK` runs on each write), an exclusion constraint or a foreign key the table declares, and a `CHECK` a parent passes down to the table, are refused as above: a column of another type than declared, or a constraint other than a key or not-null one.
   - On MySQL and MariaDB nothing of this shape can run a function of another login's on the store's writes: a partitioning function, a generated column and a `CHECK` constraint each refuse a stored function (measured on MySQL 8.4 and MariaDB 11.4, which also refuse `HASH (CRC32(path))`), and the partitioning they took on the store's session table, `KEY (path)`, evaluates no expression; a trigger runs with its definer's privileges, not the writer's. SQLite has no partitioning and no inheritance between tables.

MySQL and SQLite need neither: an unqualified call to a built-in name always calls the built-in (MySQL notes "has the same name as a native function" when a stored function takes one, and has no `CREATE OPERATOR`), and SQLite has no SQL to define a function.

Before running an older Oh My Pi against the tables, roll back. Stop the newer processes first. The statements fold each session's parts into its row's `content`, then delete the parts of, and clear `byte_len` on, only those rows whose `content` now measures `byte_len`. A session whose fold failed keeps its parts and `byte_len`, so this version still reads it whole, even when the client carries on past an error.

A session cannot be folded when its content exceeds the older version's single-value limit: 1 GB on PostgreSQL, `max_allowed_packet` on MySQL (64 MiB by default on MySQL 8, 4 MiB on 5.7, at most 1 GB), and `SQLITE_MAX_LENGTH` on SQLite (1,000,000,000 bytes by default). On PostgreSQL, on SQLite, and on MySQL in strict mode (the default), one such session makes the whole fold statement fail, so nothing is folded until that session is removed or the limit is raised.

```sql
-- PostgreSQL
BEGIN;
UPDATE omp_session_files AS s SET content = s.content || p.content
FROM (SELECT path, string_agg(content, '' ORDER BY start_offset) AS content
      FROM omp_session_files_parts GROUP BY path) AS p
WHERE p.path = s.path;
DELETE FROM omp_session_files_parts
WHERE path IN (SELECT path FROM omp_session_files WHERE octet_length(content) = byte_len);
UPDATE omp_session_files SET byte_len = NULL WHERE octet_length(content) = byte_len;
COMMIT;

-- MySQL / MariaDB (GROUP_CONCAT truncates at group_concat_max_len, 1024 bytes by default)
SET SESSION group_concat_max_len = 18446744073709551615;
START TRANSACTION;
UPDATE omp_session_files AS s
JOIN (SELECT path, GROUP_CONCAT(content ORDER BY start_offset SEPARATOR '') AS content
      FROM omp_session_files_parts GROUP BY path) AS p ON p.path = s.path
SET s.content = CONCAT(s.content, p.content)
WHERE length(CONCAT(s.content, p.content)) = s.byte_len;
DELETE FROM omp_session_files_parts
WHERE path IN (SELECT path FROM omp_session_files WHERE length(content) = byte_len);
UPDATE omp_session_files SET byte_len = NULL WHERE length(content) = byte_len;
COMMIT;

-- SQLite 3.44 or later
BEGIN;
UPDATE omp_session_files SET content = content || (
  SELECT string_agg(content, '' ORDER BY start_offset) FROM omp_session_files_parts AS p
  WHERE p.path = omp_session_files.path)
WHERE path IN (SELECT path FROM omp_session_files_parts);
DELETE FROM omp_session_files_parts
WHERE path IN (SELECT path FROM omp_session_files WHERE length(cast(content AS blob)) = byte_len);
UPDATE omp_session_files SET byte_len = NULL WHERE length(cast(content AS blob)) = byte_len;
COMMIT;
```

### Manual storage maintenance

`omp gc` previews maintenance by default; `--apply` is required to sweep unreferenced blobs, archive eligible cold sessions, checkpoint database WALs, or prune stale state. Storage maintenance is separate from model-context compaction.

The sessions phase also removes transcript rewrite temps (`.<name>.jsonl.<snowflake>.tmp`, and the same pattern beside registered `--session` files) once they are past the 5-minute write grace. A live rewrite renames its temp into place within milliseconds, so an older one was left by a killed or crashed writer.

The stale-state phase is opt-in: it runs only with `--stale` or when `gc.stale` is enabled (default off), so an unqualified `omp gc --apply` never deletes reports or replicas. It removes `custom-session-files` markers and terminal breadcrumbs whose session file no longer exists once they are a day old (a lazy session's marker names a transcript that is written only on its first turn). A breadcrumb recorded as a fresh `/new` boundary is always kept: `--continue` honors it before its transcript exists, and it is rewritten when the session materializes or replaced by the terminal's next session. For the default agent dir — or a custom agent dir named `agent`, whose parent is treated as the config root — it also expires debug report bundles (`reports/*.tar.gz`) and collab guest replicas (`collab/*.jsonl` plus their artifact directories and custom-session marker) that are both outside the newest `gc.staleRetainNewest` (default 20) and older than `gc.staleRetainDays` (default 30). A replica that a terminal breadcrumb points at, or that a running guest holds open, is kept. Stale state is pruned before the blob sweep, so blobs referenced only by an expired replica are swept in the same run.

The compress phase is opt-in as well: `--compress` or `gc.compress` (default off). It stores every file of a session (the transcript and its artifact tree) with the filesystem's transparent compression once the transcript has been idle for `gc.compressAfterDays` (default 7, `--compress-after-days`); files written more recently are skipped. Session ownership leases are taken only for sessions with files left to compress: a session is skipped while a running process holds the lease of its transcript or of any transcript nested in its artifact tree (subagent sessions, recognized by their session header whatever their file name), and those leases are held while its files are rewritten. Unlike archiving, a session with an interrupted last turn qualifies, since it stays resumable. Paths, bytes, and mtimes are unchanged and no history or stats rows are deleted, so compressed sessions stay listed, resumable, and searchable. A regular file with a single link that spans more than one filesystem block qualifies; already-compressed formats (`.gz`, `.zst`, images) are skipped. The volume holding the sessions root decides the method:

- **APFS (macOS):** detected by matching the directory's device against `apfs` entries in the mount table. `ditto --hfsCompression` writes compressed copies, with the original mtime to the nanosecond, into a fresh `.omp-gc-compress-XXXXXX` scratch directory beside the originals that holds an owner marker. A copy replaces its original only when its size and SHA-256 match and it allocates less space; immediately before the rename, the original's inode, size, and mtime must still match their values at selection and it must still have a single link, and a transcript's check and rename run under the session publish lock that serializes appends. A scratch directory left by a killed run is removed by the next `--compress --apply` run, under the sessions root and the archive root; a directory with that name and no owner marker is removed only when empty. Stats sync and the dashboard watcher skip `.omp-gc-compress-*` directories, so they never ingest a scratch copy. The replaced file is a new inode, so the next stats sync re-reads each compressed transcript once from the start; it replaces the session's rows rather than duplicating them. Appending to a compressed file stores it uncompressed again, which a later run picks up.
- **NTFS (Windows):** detected with `GetVolumeInformationW`, which must report NTFS with per-file compression support. `compact /c` sets LZNT1 compression on each file in place, keeping its inode and timestamps; later appends are stored compressed too. WOF (`compact /exe`) is not used because a write inflates the whole file.

Other filesystems report the phase as unsupported.

The strip phase is opt-in too: `--strip` or `gc.strip` (default off). Providers return state only they can read back, which omp persists so a resumed turn replays natively: signed and encrypted reasoning, the verbatim wire response kept for prompt caching, request controls, uploaded-file references. Once a transcript has been idle for `gc.stripAfterDays` (default 30, `--strip-after-days`), past every provider's cache and response retention, the phase rewrites it without that state: incremental OpenAI Responses histories, Cursor and Gemini native histories, `requestControls`, `inputTransformations`, opaque `thinkingSignature`s, `itemId`s, `redactedThinking` blocks, tool-call `thoughtSignature`s and leftover streaming state, and image `providerFile` references. Each turn then reads like one recorded by another model, which every provider already replays (reasoning as plain text, or not at all). An `entry_patch` record that sets the content of a message outside the latest replay turn loses the same state; a record every reader skips stays as written. The latest replay turn keeps everything: its run of assistant responses joined by tool results, which a provider replays as one assistant message and validates as a unit, since a resumed tool loop must replay every one of those responses' reasoning unmodified. State with no copy elsewhere also stays: reasoning source markers (`reasoning_content`), text signatures (OpenAI message phase), Anthropic message controls and native compaction blocks, OpenAI snapshot histories, and compaction entries (an OpenAI remote compaction's stored summary is only a placeholder for its encrypted history). It covers each session's transcript and the subagent transcripts in its artifact tree, under the same ownership-lease rules as compression, and archived `.jsonl.gz` sessions, which are recompressed. Lines without replay data keep their bytes, the title slot included, and the transcript keeps its mtime, so session ordering is unchanged; the stats database reparses a rewritten transcript once. The phase runs before archiving and compression so both store the stripped transcripts.

To compress without running the command, enable `gc.autoCompress` (default off). Once an interactive session has painted its first frame, omp starts a detached `omp gc --compress --apply` at low CPU priority when the last background run is at least a day old and the sessions directory supports compression. Support is checked by compressing a throwaway probe file in the sessions directory, so a volume whose compressor stores files uncompressed (macOS 27's `ditto --hfsCompression`, #16244) is not copied and hashed every day; when the check fails, `gc-auto-compress.log` records why and the next check is a day later. Launches claim the run under an OS lock keyed on the log and recheck the interval while holding it, so simultaneous launches start one child. The child outlives the launching session, writes its summary to `gc-auto-compress.log` in the agent dir, and that file's mtime marks the last run; a spawn that fails removes the log so the next launch retries. The child takes `gc.lock` like any other gc run, so a run that finds gc already running exits with that error in the log and is retried a day later. A file that compresses but does not shrink stays a candidate and is copied again on later runs. Print, RPC, and ACP launches never start it.

Journal payload I/O is streamed during blob-reference scans, archive history/stats reconciliation, gzip creation, and rollback. Active `.jsonl`, recoverable `.jsonl.*.bak`, and archived `.jsonl.gz` records all participate in reference discovery, including references in malformed JSON text. Compressed scans drain and validate the complete stream before their results can authorize deletion. Archives retain the original JSONL bytes when decompressed (less any replay data the strip phase removed), and artifact trees keep their existing layout.

Streaming avoids materializing a whole journal; it does not make GC constant-memory. A single long record, reference sets, and history/stats identity collections still consume memory. Original files and temporary compressed output also coexist during archive publication.

## Session Discovery Utilities

Discovery helpers live in `session-listing.ts`; `SessionManager` exposes project-scoped wrappers:

- `getRecentSessions(sessionDir, limit?)` -> lightweight welcome metadata, default limit 4
- `findMostRecentSession(sessionDir)` -> newest by mtime
- `findMostRecentNonEmptySession(sessionDir)` -> newest resumable content, used by `continueRecent`
- `listSessions(sessionDir, storage)` / `SessionManager.list(...)` -> project scope with lifecycle status
- `listSessionsReadOnly(...)` -> same metadata without backup recovery
- `listAllSessions(storage)` / `SessionManager.listAll()` -> project buckets under the managed sessions root, not arbitrary custom directories
- `SessionManager.listForPicker(...)` / `listAllForPicker()` -> pinned-first lists with untitled, prompt-less zero-turn stubs removed; pinned stubs remain selectable
- `resolveResumableSession(...)` -> local lookup then optional global fallback

`getRecentSessions()` sorts file stats and first looks up titles in `history.db`'s `session_titles` index; unindexed files fall back to content scanning and backfill their title. `findMostRecentSession()` reads a 4 KiB prefix. Status-enabled full/non-empty scans read that prefix plus a bounded 32 KiB tail. Scans are stat-keyed and cached; large full lists use bounded parallel workers. Normal per-directory scans also recover the newest orphaned EPERM backup when its primary JSONL is missing.

`SessionManager.list()`/`listAll()` sort pinned sessions first; raw listing helpers sort newest first. Empty filtering is picker/continue-specific, not applied to id lookup or maintenance. Resume matching is case-insensitive and accepts session id prefixes, full filename prefixes, or the id suffix after the timestamp. Explicit `sessionDir` disables global fallback unless `allowGlobalFallback: true` is requested.

## Related but Distinct: Prompt History Storage

`HistoryStorage` (`history-storage.ts`) is a separate SQLite subsystem for prompt recall/search, not session replay.

- DB: `~/.omp/agent/history.db`
- Table: `history(id, prompt, created_at, cwd, session_id, use_count)`, with unique `prompt`
- FTS5 index: `history_fts`; new prompts are indexed by an insert trigger
- Normalizes line endings and surrounding/trailing whitespace, then deduplicates prompts across the database
- Resubmission updates the latest timestamp/cwd/session provenance and increments `use_count`
- `add()` writes synchronously before returning its resolved promise; failures are logged rather than thrown
- The same DB also contains independent `session_titles` and append-only `session_recaps` tables. A session journals its idle recaps in `session_recaps` whether files or `session.storage: sql` keep it; only an in-memory session journals none. `session_titles` indexes file-backed sessions only. Idle recaps do not enter the session JSONL or model context.

Use session files for conversation graph/state replay; use `HistoryStorage` for prompt history UX.
